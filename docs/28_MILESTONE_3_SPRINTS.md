# 28 — Milestone 3 Sprints (Experience Layer)

Mirrors [16_ENGINEERING_SPRINTS.md](16_ENGINEERING_SPRINTS.md)'s format for Milestone 2, scoped to Milestone 3. Built on Engine v1.0 (`v1.0.0-engine`, [ENGINE_CHANGELOG.md](../ENGINE_CHANGELOG.md)), now frozen: every sprint below extends the engine through interfaces, registries, plugins, composition, and adapters — no engine rewrites, no breaking changes. If a feature seems to need an engine change, the sprint's own review must first prove extension is impossible before any ADR proposing one gets written.

**Implementation philosophy, stated in the brief and worth repeating here**: users should never notice the engine — only the delight it enables. Every sprint must produce something a user can touch, interact with, and remember. Motion, lighting, micro-interactions, sound, storytelling, and delight are first-class features, not polish bolted on at the end — the Creative Budget rule that started in Milestone 2 continues here, but the bar moves from "did engineering excellence increase" (assumed now) to "did emotional impact increase."

Documentation follows working code, same as Milestone 2 from Sprint 2.1 onward — this doc's entries below Sprint 3.1 stay sketch-level until their own sprint starts.

## Sprint 3.5 — AI Coffee Concierge *(complete — see [reviews/sprint-3.5-review.md](reviews/sprint-3.5-review.md))*

| | |
|---|---|
| Builds | `/concierge` — a preference questionnaire (8 signals: taste preference, sweetness, bitterness, milk, temperature, caffeine, season, time of day) feeding a deterministic, fully explainable scoring engine (`features/concierge/lib/recommendationEngine.ts`) over the real menu catalog — not an LLM call, the same "not a physics engine"-style honesty Sprint 3.4 applied to a different kind of simulation. Every recommendation carries its top pick, a positive/negative reasons list, a normalized confidence indicator, up to 2 ranked alternatives (each with its own reasons), compatible suggested ingredient customizations, and incompatible ones explicitly excluded with a reason — "never present an unexplained recommendation," the brief's own closing words. `stores/concierge-store.ts` (session-only, isolated) and `useRecommendation.ts` (React 19 `useTransition` + a request-id cancellation token, not TanStack Query — a real, documented deviation from what the Architecture Freeze anticipated, since ADR-0005's "no placeholder queries" rules out wrapping a local computation in a simulated fetch) · "Apply to Customizer" calls `customizer-store`'s own `setBaseDrink`/`addIngredient` and routes to `/customize?drink=<id>` · a real 3D integration: `CupCanvasLoader` gained an optional `cameraPreset` prop (threaded through `CupCanvas`/`CupScene`), a new `"ai"` camera preset is `CameraRig`'s first live second-preset transition (built Sprint 2.1, never exercised until now), and the recommendation's suggested customizations render as real 3D ingredient layers via `features/composer/`'s own `resolveIngredientLayers` · 2 new EventBus events (`ai:recommendation-applied`, `taste-profile:updated`) plus the first real publisher of the Sprint-0-typed `ai:recommendation-ready` |
| Depends on | `features/menu/`'s real drink catalog and tags (the scoring engine's only data source), `features/composer/`'s compatibility rules (Sprint 3.3), `stores/customizer-store.ts` (Sprint 3.2), `engine/camera/presets.ts`'s `CameraPresetName` union and `CameraRig`'s pre-built (Sprint 2.1) but never-live-tested preset-to-preset interpolation |
| Test independently | `npm run test` — 10 new unit tests (determinism, confidence bounds, a real ceiling check against `MAX_POSSIBLE_SCORE`, compatibility-validated suggestion/exclusion cases; 229 total project-wide, 34 files). `npx playwright test e2e/concierge.spec.ts` — questionnaire interaction, recommendation generation, apply-to-customizer routing, keyboard, touch, reduced motion, announcer text |
| Creative budget | Delivered: reasoning copy is specific and drink-aware ("Served cold, matching your iced preference," not "this matches your preferences"), the confidence indicator is a real, varying number (not a decorative 100%), and the 3D "reveal" (camera switch + real suggested ingredients appearing on the cup) is a genuine payoff reusing two previously-built-but-dormant engine capabilities rather than new spectacle |

**A real bug found and fixed during manual verification**: "Apply to Customizer" originally only updated store state without navigating — "one-click apply" requires actually arriving at `/customize`, not silently changing state the user would have to know to go find. Fixed with a real `router.push`, confirmed with a live click-through, not just code review.

## Sprint 3.6 — Premium Ordering Experience *(complete — see [reviews/sprint-3.6-review.md](reviews/sprint-3.6-review.md))*

| | |
|---|---|
| Builds | `features/cart/` — a real `RecipeSnapshot` model (`types.ts`) capturing a complete, self-contained copy of a composed drink (base drink, full `CustomizerSelection`, computed unit price, any applied AI recommendation) at the moment it's added to the cart — "no UI-only reconstruction," the brief's own words, built by mirroring `customizer-store`'s own live shape rather than inventing a parallel one. `lib/buildRecipeSnapshot.ts` (pure, tested) builds one; `customizer-store.ts`'s new `loadRecipeSnapshot` restores one for editing — a lossless round trip. `stores/cart-store.ts` (built to [18_ENGINEERING_CONTRACTS.md](18_ENGINEERING_CONTRACTS.md)'s pre-designed, `localStorage`-backed contract, extended for this sprint's richer brief: quantity editing, reordering, session favorites, `placeOrder()`). UI: `AddToCartButton` (a real "fly to cart" animation via a new `cartIconAnchor` bridge store — the same cross-tree-boundary pattern `useCupKeyboardControls`'s `keyboardRotationDelta` established in Milestone 1, reused for a DOM-position handoff instead), `CartIcon`/`MiniCart` (navbar, `Sheet`-based), the full `/cart` page, `/checkout` (a minimal, honestly-scoped name/email form — no fake payment fields, this project has no backend or payment gateway), and `/checkout/confirmation` (a real checkmark-reveal premium moment). 3 new EventBus events (`cart:item-added`/`-removed`/`-updated`) plus the first real emitters of the Sprint-0-typed `checkout:started`/`checkout:completed` |
| Depends on | `stores/customizer-store.ts` (Sprint 3.2, extended with `appliedRecommendationId`/`markRecommendationApplied`/`loadRecipeSnapshot`), `features/composer/`'s pricing formula (extracted into a shared `calculateIngredientsTotal.ts` so the cart and `RecipeSummary` never compute a price two different ways), `features/concierge/`'s recommendation-application flow (extended to record which recommendation, if any, a recipe traces back to) |
| Test independently | `npm run test` — 32 new unit tests (`buildRecipeSnapshot.test.ts`, `cart-store.test.ts`, `calculateIngredientsTotal.test.ts`, plus `customizer-store.test.ts`'s new `appliedRecommendationId` coverage; 257 total project-wide, 37 files). `npx playwright test e2e/cart.spec.ts` — 12 tests × 3 browsers: add-to-cart, mini-cart, recipe merging, quantity/removal, favorites, edit-routes-back-to-customizer, checkout validation, empty states, screen-reader announcements, keyboard, touch, reduced motion |
| Creative budget | Delivered: a real, working "cup flies into cart" animation (a ghost element animating from the Add-to-Cart button to the navbar's cart icon, using actual measured DOM positions, not a canned CSS keyframe), a genuine checkmark-reveal order confirmation, and a cart-badge "pop" on count changes — all skip cleanly under reduced motion (a durable text/badge state change either way, never a silent no-op) |

**Two real bugs found and fixed during manual verification, not shipped**: (1) the customizer panel's own internal scroll can carry the whole window down far enough to hide the fixed navbar — `AddToCartButton` now snaps the window back to the top before measuring the fly-animation's target, so the cart icon is always a real, visible destination regardless of scroll position. (2) every `Button` rendered as a `<Link>` in the new cart UI was missing `nativeButton={false}` (the established convention `DrinkDetailDialog.tsx`/`HeroCopy.tsx` already use for exactly this), producing a real Base UI console warning on every page load — fixed across all 7 occurrences.

**A real regression found and fixed during the full e2e regression run**: adding `CartAnnouncer` to the global navbar meant `/customize` and `/concierge` could now have *two* simultaneous `role="status"` live regions, breaking two pre-existing Sprint 3.3/3.5 e2e tests that assumed only one existed. Fixed by giving every announcer (`IngredientAnnouncer`, `RecommendationAnnouncer`, `CartAnnouncer`) a distinguishing `aria-label` — a real, correct accessibility improvement for screen-reader users with multiple simultaneous live regions, not just a test-targeting convenience — and updating the two tests to target their own region by name.
