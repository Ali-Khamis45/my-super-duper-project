# Sprint 3.4 — Liquid & Physics Experience: Review

The first physically-believable coffee experience: a lightweight, deterministic spring-damper simulation — not a physics engine — giving the coffee surface real tilt/inertia in response to cup rotation, decaying ripples on drag-start/release, and foam/ice as slower, lagged followers of the same signal. Built exactly to the design [04_MOTION_ENGINE.md](../04_MOTION_ENGINE.md) and [13_SHADER_ARCHITECTURE.md](../13_SHADER_ARCHITECTURE.md) sketched two sprints ago and the Architecture Freeze's "Coffee Liquid Physics" scenario validated on paper, through Engine v1.0's existing extension points (Shader Manager's `onBeforeCompile` convention, the material cache, the registry, `QualityPolicy`, the EventBus) — zero engine rewrites.

**Scale**: 9 new source files (`engine/physics/` — `types.ts`, `liquidPhysics.ts`, `liquidPhysics.test.ts`, `index.ts` — plus `engine/shaders/coffee/liquidDeformation.ts`, `engine/shaders/foam/foamLagDeformation.ts`, `features/hero-cup/hooks/useLiquidPhysics.ts`, `features/hero-cup/parts/ProceduralIngredientIce.tsx`, `e2e/physics.spec.ts`), 23 modified files (`useCupInteractionState.ts` gained `velocityRef`; `CoffeeSurface.ts`/`FoamSurface.ts`/`applyFresnelRim.ts` composed real vertex displacement alongside the existing fresnel rim; `CupAssembly.tsx` and both procedural parts wired to `physicsRef`; `qualityPolicy.ts` reshaped `coffeePhysicsQuality` into a graded policy; `engine/events/types.ts` gained 4 events; composer's ice routing; 6 docs). 20 new unit tests (219 total project-wide, 33 files, all passing). A new `e2e/physics.spec.ts` (7 tests, up to 3 browsers — the long-running soak is Chromium-only).

## Architecture review

**No engine files touched beyond the sanctioned extension points**: `engine/physics/` is a genuinely new, small engine module (the same "cross-cutting, not feature-owned" reasoning as `engine/materials`/`engine/shaders` — physics values are consumed by `hero-cup` parts but the simulation itself has no `hero-cup`-specific knowledge). `engine/events/types.ts` gained `physics:started`/`-settled`, `liquid:disturbed`/`-stabilized` — the brief's own "Extend the Event Catalog only where necessary." All four map directly to real, distinct settle-state transitions the simulation actually computes (`liquidSettled` vs. the coarser `settled` — see Physics Review below), not speculative additions.

**Built to a two-sprint-old design, not improvised**: `13_SHADER_ARCHITECTURE.md`'s Coffee section named `uTiltAngle` and a fixed-size `{ origin, startTime }` ripple array as the target design during Sprint 2.4 planning; `04_MOTION_ENGINE.md` named the exact `velocityRef` extension `useCupInteractionState` would need, during the Architecture Freeze. Both are implemented essentially as specified — checked directly against those docs during implementation, not reconstructed from scratch. The one genuine judgment call beyond what was pre-designed: packing the ripple array into `vec4` uniforms (`uRippleAmplitude`/`uRippleElapsed`) rather than a GLSL array-of-structs, and foam getting no ripple array at all (a single lagged scalar) — both real, reasoned simplifications, not deviations from anything actually specified.

**One owner per animated property, verified against the brief's own rule**: `useLiquidPhysics` is the single `useFrame` that *computes* the simulation (one call, `CupAssembly`-level, regardless of how many parts read it). Each part (`ProceduralCoffee`/`ProceduralFoam`/`ProceduralIngredientIce`) owns *applying* the result to its own material/transform in its own `useFrame` — the same split `ProceduralSteam` already established for its own `uTime`/`uOpacity` (Sprint 2.4). No two systems write the same property: `useCupInteractionState` owns `rotationYRef` (user input → rotation), `useLiquidPhysics` owns everything physics-derived, each part owns only its own material/transform.

**A real composability bug avoided, not discovered in production**: `material.onBeforeCompile = (shader) => {...}` is an assignment, not a subscription — a naive second call from a new "add liquid physics" function would have silently overwritten Sprint 2.4's fresnel rim rather than adding to it. Caught during design (not after shipping a broken rim), fixed by extracting `injectFresnelRim`/`injectLiquidDeformation`/`injectFoamLagDeformation` as composable pure functions that `CoffeeSurface.ts`/`FoamSurface.ts` call together inside one combined callback — `applyFresnelRim` itself (foam's Sprint 2.4 entry point, still used exactly as before by anything not needing the composed version) is unchanged.

**`coffeePhysicsQuality` reshaped at its first real consumer**: the Sprint 2.5 placeholder was a plain `"off" | "full"` — a boolean-in-disguise `qualityPolicy.ts`'s own doc comment already named as the one documented exception (`bloomEnabled`) to "every parameter is a scale." This sprint's explicit "never disable physics entirely" directly conflicts with a second boolean exception, so it was reshaped into a graded `{ intensity, maxActiveRipples, secondaryMotion }` before writing any consumer code — the same "shape it correctly at its first real consumer" precedent `materialOverrides`/`colorway` established in Sprint 3.2, verified to have zero prior callers before changing it.

## Physics review

**Deterministic, verified by test, not asserted**: `stepLiquidPhysics` is a pure function — no `Math.random()`, no wall-clock reads, `dt` is caller-supplied. A dedicated unit test runs two independent state objects through an identical input sequence and asserts `toEqual` (deep equality) on the result — real determinism, not "looks stable."

**Convergence and bounds, verified by test**: sustained angular velocity drives tilt toward a target, then holding still lets it decay back below a tight epsilon (< 0.001 rad); tilt is hard-clamped to ±0.09 rad (~5°) regardless of how extreme the input velocity is — a real spring can transiently overshoot its own target (part of the "wobble" feel), so the clamp is a deliberate safety bound on top of the spring, not a substitute for one (discovered via a failing test during implementation: an unclamped spring given `angularVelocity: 50` overshot to ~0.090225 rad before the clamp was added).

**Settle ordering is real, not asserted**: `liquidSettled` (tilt + ripples) and `settled` (liquid + foam + ice) are two distinct, separately-computed flags — a dedicated test disturbs the system and records the exact simulation step each flag first flips true, asserting `liquidSettled` never settles *after* `settled`. This is what makes `liquid:stabilized` firing before `physics:settled` a real, tested guarantee, not incidental ordering that happened to work in manual testing.

**Ripple-cap behavior, verified by test**: `triggerRipple` never activates more than `policy.maxActiveRipples` concurrently ("reduce ripple resolution" at lower tiers) but still plays *a* ripple rather than silently declining the disturbance ("never disable physics entirely") — a real cap-respecting test, not just "it compiles."

**A genuine design tension, resolved and documented, not glossed over**: real liquid sloshing from a Y-axis spin would be centrifugal (surface dips at center, rises at the rim), not a directional tilt. This sprint's tilt is a directional linear-plane displacement instead — a deliberate "perceptually believable, not physically accurate" choice (the brief's own closing words), cheaper than a radial displacement and reads as "the cup is being nudged/tilted" rather than "the cup is spinning very fast," which is the more relatable, coffee-shop-relevant sensation for a drag gesture. Recorded here rather than left for a future reader to wonder whether it's an oversight.

## Shader review

**Injection points verified against the installed Three.js source, not assumed** — same discipline `applyFresnelRim`'s own doc comment already established for the fragment side: `#include <begin_vertex>` is where `transformed` is declared and set; injecting immediately after it (not before, where `transformed` wouldn't exist yet) is the only correct point to displace it. Local Z maps to world Y ("height") after `ProceduralCoffee`/`ProceduralFoam`'s existing `[-Math.PI / 2, 0, 0]` mesh rotation — checked against that rotation, not assumed from a different part's convention.

**Foam deliberately gets less than coffee, not a copy of it**: the brief is explicit — "Slight lag behind liquid. Subtle wobble. Very low amplitude. Never noisy." Foam's shader (`foamLagDeformation.ts`) has exactly one uniform (`uFoamLag`) and no ripple array at all; a second full ripple system on foam would have been precisely the "noisy" it's told not to be. `uFoamLag` itself is computed as a lower-amplitude, lower-stiffness spring follower of the liquid's own `tiltAngle` in `engine/physics/liquidPhysics.ts` — foam visibly lags because it's genuinely driven *from* a slower spring reading the same signal, not a hand-tuned delay hack.

**A real, accepted simplification**: neither shader recomputes vertex normals after displacement. At this amplitude (max ~0.09 rad tilt, smaller ripples, even smaller foam lag) the lighting error from stale normals is not visually significant under manual inspection; a correct analytic or finite-difference normal recompute would add real per-vertex cost for an effect nobody would notice is slightly mis-lit. If a future Creative Director Review disagrees, this is the first place to revisit.

**Ice gets transform-level animation, not a third vertex shader** — a deliberate, reasoned split: coffee/foam are continuous disc surfaces where per-vertex displacement is the natural technique; ice is a small discrete object (the same shared torus geometry every non-distinct ingredient uses) where a cheap `useFrame`-driven group-transform bob/drift is simpler, cheaper, and visually equivalent — "if a cheaper solution looks better, it is the correct solution," the brief's own words.

## Performance review

**Adaptive quality is real, not cosmetic**: `qualityPolicy.ts`'s `coffeePhysics.intensity` is verified never 0 at any of the 5 tiers (a dedicated test), and monotonically non-increasing from `ultra` to `minimal` (another dedicated test) — `ultra`/`high` run full intensity with all 4 ripple slots and independent foam/ice springs; `medium` scales to 70% intensity; `low`/`minimal` drop to 45%/25% intensity, cap ripples to 2/1 slots, and switch foam/ice to a cheap direct alias of the primary signal instead of running their own spring integration — "reduce simulation frequency, ripple resolution, wave complexity, secondary motion," each named brief requirement maps to one specific, testable policy field.

**Reuse verified, not assumed**: one shared `TorusGeometry` instance still serves ice (no new geometry allocated), the fixed-size ripple array is mutated in place every frame (`Array.from` allocates it exactly once, at `createLiquidPhysicsState()`), and `updateLiquidDeformationUniforms`/`updateFoamLagUniforms` write into already-allocated `THREE.Vector4` uniform values (`.set(...)`) rather than constructing new ones every frame.

**Real-browser verification**: manual verification in a fresh browser session (drag-release on the Hero route, keyboard-driven rotation, touch drag, reduced motion, and adding the Ice Cubes ingredient on `/customize`) produced zero console/page errors across every path — meaningful specifically because a GLSL compile error in either shader would have surfaced immediately as a console error the moment the coffee/foam material first mounts, and didn't. This session showed none of Sprint 3.3's documented SwiftShader crash instability; that finding is understood to have been session-specific (a very long-running dev session), not something this sprint's code changed.

**Two environmental e2e findings, re-confirmed rather than newly caused**:
1. Two of `physics.spec.ts`'s own tests ("repeated drag/release cycles," "adding Ice Cubes") pass cleanly in isolation and at reduced parallelism but occasionally time out under this suite's full default 8-way parallelism on this single dev machine — the same class of resource-contention flake `playwright.config.ts`'s own comments and Sprint 3.2/3.3's reviews already document for other tests in this suite. Not new, not an app defect (confirmed by isolated re-runs passing cleanly).
2. The full regression run reproduced the exact same pre-existing Firefox Hero-route dark-theme visual-regression diff Sprint 3.3's review first documented (78,132 pixels, 0.09 ratio) — checked directly by comparing this run's diff image against that one: identical pixel count and pattern, confined entirely to the WebGL-rendered cup mesh. Since this sprint *did* modify the coffee shader (the exact material visible in that diff), this was verified with extra scrutiny rather than assumed unrelated — the identical magnitude and pattern is strong evidence this sprint's changes did not worsen or alter it, not just a convenient assumption.
3. The pre-existing WebKit reduced-motion `customizer.spec.ts` automation quirk (documented in Sprint 3.3's review as a known Playwright/WebKit-specific click-vs-keyboard timing issue, unrelated to physics) also reproduced identically — untouched cosmetic-swatch code, not this sprint's concern.

**A real test-timing-budget lesson, fixed rather than worked around with a blanket config change**: two of `physics.spec.ts`'s own tests (5 repeated drag cycles; a periodic-disturbance soak) initially exceeded even a 90s explicit timeout on this software-rendered dev machine. Rather than keep inflating the timeout, the long-running soak was scaled down (6 disturb cycles → 3, matching `long-running.spec.ts`'s own precedent — "a literal 30-minute run wasn't executed this session... run the real duration as a scheduled/nightly job") and both tests now pass reliably within a 90s budget.

## Accessibility review

**Keyboard parity, a real gap found and fixed during implementation, not shipped incomplete**: `useCupInteractionState`'s internal `velocityRef` was previously only ever written by drag/touch pointer events — keyboard-driven rotation (`ArrowLeft`/`ArrowRight`) applied a rotation delta directly and never touched velocity at all. Since `useLiquidPhysics` reads `velocityRef` as its sole input, keyboard users would have gotten a fully inert liquid — zero tilt, zero ripple, zero physics response — a direct violation of the brief's own "Keyboard users must experience the same visual state transitions." Fixed by having the keyboard-rotation path also apply a one-frame velocity impulse, plus a new decay branch so that impulse settles back to 0 on its own (keyboard rotation never transitions through the drag-release `"rotate"` inertia-coast state, which is what previously handled velocity decay). Verified live via e2e: 6 `ArrowRight` presses produce zero console errors through the same physics path a drag would.

**Reduced motion — "disable outright," this project's established policy, applied consistently**: under reduced motion, tilt uses direct, non-overshooting interpolation (`lerpTowards`) instead of the spring-damper oscillation, and new ripples are never triggered at all (an already-in-flight ripple from before a toggle still finishes decaying rather than freezing abruptly). A dedicated unit test confirms the reduced-motion tilt path never overshoots its target. Verified live via e2e: a full drag-release cycle under `emulateMedia({ reducedMotion: "reduce" })` produces zero console errors.

**Touch parity**: touch-drag reaches the identical `velocityRef` path as mouse-drag (same `useCupInteractionState` pointer handling, unchanged this sprint) — verified live via e2e with `hasTouch: true`.

**Nothing new to announce**: this sprint has no new interactive controls (physics is a passive response to existing drag/keyboard/touch rotation, not a new affordance) — `IngredientAnnouncer` (Sprint 3.3) and every existing `aria-label`/`aria-checked` state are unaffected.

## Creative Director Review

**Delivered, and load-bearing, not decorative**: "Coffee continues moving after the cup stops" is literally the inertia-coast (`useCupInteractionState`'s pre-existing `"rotate"` state) driving `velocityRef`, which now also drives visible liquid tilt for the first time — the *existing* inertia mechanic gained a second, real payoff this sprint, rather than a separate new animation being bolted on next to it. "Foam gently settles" is the lagged-follower spring, visibly a half-beat behind the liquid's own settle. "Ice slightly drifts" is real, independent, always-on ambient motion (`resolveIceIdleOffset`), deliberately never fully at rest even when the rest of the system has settled — matching "float naturally" rather than "float only while disturbed."

**Honestly scoped, not oversold**: "Liquid catches light differently while moving" is not separately implemented — the existing PBR lighting model (unchanged from Sprint 2.3) simply responds to the real vertex displacement automatically, which is a genuine, real effect but not a bespoke shading pass built for this sprint; worth naming precisely rather than implying more new shading work happened than did. The tilt/ripple amplitude is deliberately small (~5° max) — "motion feels expensive, not exaggerated" was treated as the actual bar, not a soft suggestion, and this is exactly the kind of subjective creative-quality call [24_RISK_REGISTER.md](../24_RISK_REGISTER.md)'s R-12 already flagged as needing a real CDR pass to fully validate, not something this implementation-and-engineering-focused review alone can close out.

## Retrospective

### Technical debt

- Vertex normals aren't recomputed after coffee/foam displacement (Shader Review) — a real, accepted simplification, revisit if a future CDR pass finds the lighting visibly off during an active drag.
- Ripple origin angle is a deterministic golden-angle sequence, not mapped to the actual drag pointer's position on the rim — a real, reasoned simplification (the brief doesn't require physical accuracy), but the ripple's visual origin is currently unrelated to *where* on the cup the user's pointer actually was.

### Architectural observations

- The `useLiquidPhysics` (compute) / per-part `useFrame` (apply) split is this sprint's clearest example of "every visual motion has exactly one owner" holding up on a case with three consumers (coffee, foam, ice) instead of Sprint 3.3's one-consumer precedent (`resolveIngredientLayers`) — the pattern generalized cleanly.
- `injectFresnelRim`'s extraction (a pure function callers compose, versus the original version that unconditionally assigned `material.onBeforeCompile` itself) is a real, minimal, backward-compatible refactor — foam's original Sprint 2.4 call path (`applyFresnelRim` alone) is byte-for-byte unchanged for any future caller that only needs the fresnel rim.
- `coffeePhysicsQuality`'s reshape is the second time this project has had to correct a `"off" | "full"`-style placeholder into a graded scale at its first real consumer (the same shape `bloomEnabled` was *not* — bloom's binary-at-one-tier design was a deliberate, reasoned exception from the start). Worth remembering for any future placeholder field: a two-value union is worth a second look before its first real consumer locks it in, especially if "never fully disable" is a plausible future requirement.

### Possible improvements

- Ripple origin could be derived from the actual drag pointer position (a real 2D-screen-to-rim-angle mapping) if a future pass wants the ripple to visibly originate from where the user's finger/cursor actually is, rather than a deterministic but pointer-independent sequence.
- `uPhysicsIntensity` (the shared Uniform Manager's dormant "Milestone 3" field) was deliberately left unpublished this sprint in favor of per-instance uniforms already carrying pre-scaled intensity values — publishing it for a *second*, non-redundant shader-side use (e.g. ripple spatial frequency/sharpness) would be a reasonable, self-contained follow-up, not required by this sprint's brief.

## Sign-off

20 new unit tests (219 total, 33 files, all passing — including determinism, convergence, settle-ordering, and adaptive-quality-scaling coverage for the physics core), a new 7-test e2e suite (`physics.spec.ts`, all passing individually/at reduced parallelism across Chromium/Firefox/WebKit where applicable), zero engine files touched beyond the sanctioned event-catalog/quality-policy extensions, zero regression in Sprint 3.1–3.3 functionality (`tsc --noEmit`, `eslint`, `next build` all clean). A real accessibility gap (keyboard users getting zero physics response) was found and fixed during implementation, not shipped incomplete. Two pre-existing, unrelated environmental e2e findings were re-confirmed identical to their Sprint 3.3 documentation, with the one directly touching this sprint's own changed code (the Firefox coffee-shader visual-regression diff) given extra direct-comparison scrutiny rather than assumed unrelated. Waiting for approval before Sprint 3.5 (AI Barista) begins, per explicit instruction.
