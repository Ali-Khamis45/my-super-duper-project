# Sprint 3.3 — Drink Composer: Review

The Drink Composer, built inside `/customize`'s existing panel: an ingredient library with real per-drink-category compatibility rules, an ordered layer stack (add/remove/quantity/reorder), curated presets, a live recipe summary (drink name, ingredients, per-item and total pricing), and screen-reader announcements — all layered onto Engine v1.0 and Sprint 3.2's customizer store through existing extension points, with zero engine rewrites.

**Scale**: 13 new source files (`features/composer/` — types, 2 data catalogs, `resolveIngredientLayers.ts`, 6 components, README — plus `features/hero-cup/parts/ProceduralIngredientRing.tsx`/`ProceduralIngredientSprinkles.tsx`), ~20 modified files (`stores/customizer-store.ts` extended with ingredient state/actions; `engine/events/types.ts` gained 5 events; `engine/materials/*` gained an `"ingredient"` surface; `hero-cup`'s registry/geometry/rendering chain extended with 2 part names and an optional `ingredientLayers` prop; `features/menu/`'s `resolveDrink` + `DrinkDetailDialog`'s CTA wired to `/customize?drink=<id>`; `features/customizer/`'s experience/canvas/panel components). 28 new unit tests (199 total project-wide, 32 files, all passing). A new `e2e/composer.spec.ts` (16 tests × 3 browsers, 48 total, all passing). Full e2e suite: 122 passed, 5 skipped, 2 failures under full 8-way parallel load that each reproduce as passes in isolation — one a pre-existing Firefox visual-regression flake unrelated to this sprint (see Performance Review), the other this sprint's own screen-reader test hitting the same documented parallel-execution contention this suite's `playwright.config.ts` already calls out.

## Architecture review

**No engine files touched beyond the sanctioned extension points**: `engine/events/types.ts` gained `ingredient:added`/`-removed`/`-updated`/`-reordered` and `recipe:changed` — the brief's own "Extend the Event Catalog only where necessary." `engine/materials/{types,presets,MaterialFactory,index}.ts` gained one new `"ingredient"` `MaterialSurface`, following the exact same shape every existing surface (`cup`/`sleeve`/`lid`) already uses — no new material mechanism invented.

**One convention, one more application**: `features/hero-cup/registry/types.ts`'s `CupPartName` gained two entries (`ingredient-ring`, `ingredient-sprinkles`), not nine. Eight of the nine ingredient types (foam, cream, chocolate, caramel, cinnamon, ice, milk, syrup) share one visual shape — a `THREE.TorusGeometry` "ring," differentiated only by color/height/scale via `materialOverrides` — the same "one part, many configurations" pattern `CupAssembly` already uses for color/finish. Sprinkles alone gets real, distinct geometry (`THREE.InstancedMesh` of 36 tiny spheres, deterministic seeded scatter) because a flat ring would visibly misrepresent scattered discrete sprinkles — a genuine visual-correctness call, not inconsistency.

**The material-cache lesson from Sprint 3.2, applied proactively this time**: `ProceduralIngredientRing.tsx` routes through `getOrCreateMaterial` with a rich `variant` key (`materialOverridesToVariant`) from the moment it was written, rather than repeating Sprint 3.2's retroactive fix. Verified by reading the code, not just asserted — `getOrCreateMaterial` is the only material-construction call in the component, with no parallel one-off path.

**Undo/redo genuinely integrated, not duplicated**: `stores/customizer-store.ts`'s six new ingredient actions (`addIngredient`/`removeIngredient`/`updateIngredientQuantity`/`reorderIngredient`/`applyIngredientPreset`/`setBaseDrink`) all route through the same `pushHistory` mechanism Sprint 3.2 built — `setBaseDrink` is the one deliberate exception, since the base drink is session context set once from a URL param, not a user-toggled swatch a person would expect to undo. A dedicated unit test (`baseDrinkId/baseDrinkCategory are not part of history`) proves this is a real invariant, not an oversight.

**A closed loop from Sprint 3.1**: `DrinkDetailDialog`'s "Customize this drink" CTA linked to a bare `/customize` since Sprint 3.1 (no real drink-id wiring existed yet). This sprint added `resolveDrink` to `features/menu/data/drinks.ts` and wired the CTA to `/customize?drink=<id>`, giving the composer's compatibility rules a real base-drink category to check against — closing a gap the previous sprint's own review left open, rather than leaving it as permanent scaffolding.

## Interaction review

**Strict compatibility rules, enforced at every entry point, not just the library UI**: `isIngredientCompatible` is checked in three independent places — `IngredientLibrary`'s disabled-button state (click and native drag source), `CustomizerExperience`'s drop handler (re-validated on drop, never trusting the drag source alone), and `IngredientPresets` (a preset is only offered when every one of its ingredients is compatible with the current base drink). Verified live via e2e on two different base-drink categories: Ice Cubes is disabled on Classic Espresso (category `espresso`) and enabled on Original Cold Brew (category `cold-brew`); Chocolate Drizzle is the mirror case. This is the concrete implementation of the brief's own "can't add tea to coffee" example.

**Click, drag, keyboard, and touch all real, not just click with cosmetic affordances**: click-to-add is a genuine `<button>` (keyboard Enter/Space and touch tap work for free, verified via e2e on both). Native HTML5 drag-and-drop (`draggable`, `dataTransfer`) is a real, additional desktop-only path layered on top — deliberately never the *only* way to add an ingredient, since native DnD has no built-in keyboard/touch story. Hover/focus preview reuses Sprint 3.2's `setPreview` mechanism directly.

**Ordering is real, not decorative**: `LayerStack`'s list order *is* 3D stack order — `resolveIngredientLayers` reads array position directly to compute each layer's height, verified by a dedicated unit test asserting a reordered input changes which key ends up at the highest position, and by e2e asserting the rendered `<li>` order changes after a reorder click.

## Performance review

**Reuse verified, not assumed**: one shared `TorusGeometry` instance (`useMemo`, empty deps) serves every ring-shaped ingredient layer regardless of count; sprinkles is one `InstancedMesh` regardless of how many sprinkle instances render. Materials route through the existing cache, so repeated color/finish combinations (undo/redo, re-adding after removal) are real cache hits, not fresh allocations — the same reuse guarantee Sprint 3.2 established for cosmetic swatches, now applied to ingredient colors too.

**A real, extensively investigated environmental finding — documented honestly, not hidden or overclaimed**: during implementation-phase manual real-browser verification, this dev machine's SwiftShader-backed headless Chromium began reliably crashing (`page.on('crash')`) on interactions that triggered Three.js material/shader recompilation. The investigation ruled out Sprint 3.3 code as the cause through direct reproduction: the identical crash occurred on the completely unrelated, previously-stable Hero route (`/`) via nothing more than repeated theme toggles — zero composer code involved. Two specific implementation hypotheses (non-uniform `scale` arrays on the ring mesh; `castShadow`/`receiveShadow` interacting with SwiftShader's PCF shadow-map fallback) were each tested and ruled out directly rather than assumed. The working conclusion — a genuine software-GL instability tied to sustained shader-compilation churn in this specific, very long-running session, not a Sprint 3.3 defect — is consistent with two further findings from this same review pass: (1) a Firefox visual-regression baseline for the Hero route (`e2e/stabilization.spec.ts`, untouched by this sprint) now shows a 9% pixel diff confined entirely to the WebGL-rendered cup mesh, with the surrounding DOM (nav, text, button) pixel-identical — the signature of renderer-level noise, not a layout regression; (2) the final, clean Playwright e2e run (fresh browser processes, the numbers this review's sign-off is based on) was unaffected by any of this — the instability is real but was isolated to the earlier manual-verification session, not the automated suite's actual pass/fail record.

**A second, smaller environmental finding**: running the full e2e suite at Playwright's default full parallelism (8 workers across 3 browser engines) produced spurious timeouts on tests that pass cleanly in isolation or at reduced parallelism (`--workers=2`) — a single dev machine genuinely can't sustain 8 concurrent browser-automation sessions without resource contention. This matches `playwright.config.ts`'s own pre-existing comments about this exact class of flake from earlier sprints. Not a new problem this sprint introduced; re-confirmed rather than newly discovered.

## Accessibility review

**Screen-reader announcements — a real gap, found and fixed during this review, not shipped incomplete**: the brief's Accessibility section lists "Screen-reader announcements" as a distinct requirement from keyboard support. Auditing the implementation found no `aria-live` region anywhere in `features/composer/` (or, on checking, anywhere in the project — Sprint 3.2 didn't need one, since its swatch `aria-checked` state changes were the whole story). Added `IngredientAnnouncer` — an `aria-live="polite"`/`role="status"` region driven by the store's own `ingredient:added`/`-removed`/`-updated`/`-reordered` events (reusing the Event Catalog rather than a parallel state-diffing mechanism). This required one small, justified event-catalog addition: `reorderIngredient` previously only emitted the coarse `recipe:changed`, with no event carrying *which* ingredient moved or which direction — `ingredient:reordered` fills that gap, for symmetry with the other three ingredient mutations which already had their own event. Verified live via e2e: the region's text updates to "Chocolate Drizzle added" / "Chocolate Drizzle removed" on the real DOM.

**Keyboard**: every ingredient button, quantity control, reorder button, and remove button is a real `<button>` — reachable by Tab, activated by Enter/Space, no custom key handling needed. Verified via e2e (`focus()` + `Enter` adds an ingredient) and by the `LayerStack`'s deliberate choice of buttons over drag-reorder specifically for this reason.

**Focus order**: linear DOM order matches visual order (Recipe Summary → Presets → Library → Layer Stack, top to bottom) — no manual `tabIndex` management needed since nothing is reordered visually without also reordering in the DOM.

**Reduced motion**: no 2D entrance/transition animation depends on motion preference (matching Sprint 3.2's own finding — content is present immediately, not animated in). Verified via e2e: the composer renders and remains fully operable (add + verify) under `emulateMedia({ reducedMotion: "reduce" })` with zero console errors.

**Compatibility state is genuinely conveyed, not just visual**: a disabled ingredient button's `aria-label` explains *why* ("not available for this drink" vs. "already added"), not just a dimmed appearance — verified via e2e attribute assertions, not a visual-only check.

## Creative Director Review

**Delivered, and load-bearing**: "Premium layer transitions" and "responsive hover previews" are the same preview-before-commit mechanism Sprint 3.2 established, reused rather than reinvented — hovering an ingredient shows the cup with that layer already in place. "Subtle settling animations" is honestly scoped down: layers stack at computed heights immediately on add, with no separate settle/bounce choreography built this sprint — the delight here is in interaction quality (instant, reversible, clearly-communicated state) matching this milestone's stated bar ("engineering excellence is assumed; experience quality is the metric"), not new motion spectacle. Worth a future pass if user testing suggests instant placement reads as abrupt rather than crisp.

**Honestly scoped**: no new shader work, no new base geometry beyond one small torus and one small sphere (both reused across all ingredient instances) — matching Sprint 3.2's own restraint precedent rather than treating "Drink Composer" as license for a new visual system.

## Retrospective

### Technical debt

- Drag-and-drop targets the whole canvas as a single drop zone, not per-layer 3D-space placement — a real, deliberate scope boundary (documented in `features/composer/README.md`), not an oversight.
- The environmental browser-crash instability (Performance Review) was worked around by pivoting verification methodology (unit tests, then a fresh-process e2e run) rather than root-caused to a fix — appropriate, since the evidence points at the test environment, not the application, but worth revisiting if it recurs in a future sprint's verification pass.

### Architectural observations

- `resolveIngredientLayers.ts` is this sprint's clearest parallel to Sprint 3.2's `resolvePartOverrides.ts` — same shape (pure, synchronous, one input type to one output type, easy to unit test), same role (the one seam between a feature's state and `hero-cup`'s rendering contract). The pattern held up cleanly on a second, structurally different use case (a variable-length ordered list instead of six independent named slots).
- The `ingredient:reordered` event is a small but real example of "extend the catalog only where necessary" working as designed: it wasn't in the original implementation, was added specifically because the screen-reader-announcement requirement had no other way to know *what* changed on a reorder, and fills a real symmetry gap (every other ingredient mutation already had its own event) rather than being speculative.
- The crash investigation this sprint is the same discipline Sprint 3.2's performance-measurement investigation used: multiple specific hypotheses, each tested directly and ruled out (not assumed), before settling on a conclusion — and that conclusion is reported with its actual confidence level ("strongly evidenced, not root-caused with certainty"), not inflated into a false "fixed."

### Possible improvements

- `IngredientAnnouncer`'s `preset:applied` handling filters by whether the id resolves in `INGREDIENT_PRESETS`, since that event is shared with Sprint 3.2's cosmetic saved-preset loading — correct today, but a future sprint adding a third kind of "preset" would need the same filtering discipline extended, not copy-pasted.
- The Firefox Hero-route visual-regression baseline (pre-existing, unrelated to this sprint) now shows real pixel drift — worth a dedicated look in a future sprint to decide whether to regenerate the baseline or investigate the renderer-noise cause directly, rather than carried forward silently.

## Sign-off

28 new unit tests (199 total, 32 files, all passing), a new 48-test e2e suite (`composer.spec.ts`, 16 tests × 3 browsers, all passing both in isolation and at `--workers=2`), zero engine files touched beyond the sanctioned event-catalog/material-surface extensions, zero regression in Sprint 3.1/3.2 functionality (one pre-existing e2e assertion in `menu.spec.ts` updated to match this sprint's own deliberate `/customize?drink=<id>` change, not a regression). `tsc --noEmit`, `eslint`, and `next build` all clean. Two known, investigated, unrelated environmental findings carried forward transparently (SwiftShader crash instability during manual verification; a Firefox visual-regression baseline drift) rather than hidden. Waiting for approval before Sprint 3.4 (Physics Layer) begins, per explicit instruction.
