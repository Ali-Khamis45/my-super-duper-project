# Sprint 2.5 — Runtime Optimization & Adaptive Quality: Review

Sprint 2.5 built the systems that continuously observe and adapt rendering quality/performance/memory at runtime: the Adaptive Quality Manager, GPU Budget Manager, Memory Pressure Detection, Runtime Profiler, and — the sprint's most consequential finding — the always-on Production Telemetry sampler that Sprint 2.1's foundation was missing. Not a visual-features sprint, per its brief ("No Steam improvements. No Coffee Physics. No Ingredient Physics. No Storytelling. No AI. No Commerce.").

**Scale**: 9 new source files (`engine/performance/`), 9 modified files (`types.ts`, `index.ts`, `assetQuality.ts`, `CupCanvas.tsx`, `CupScene.tsx`, `DevPanel.tsx`, `DevDiagnosticsProbe.tsx`, `engine/shaders/common/uniforms.ts`, `engine/events/types.ts`, `engine/analytics/events.ts` + `eventBridge.ts`), 30 new unit tests (146 total project-wide, 25 test files). `tsc`, `eslint`, `next build` all clean. Real-browser CPU-throttle stress test (headless Chrome, CDP `Emulation.setCPUThrottlingRate`) confirms the adaptive stepping algorithm actually runs and steps the live tier under genuinely degraded frame rates — not just unit-tested in isolation.

## Architecture review

**`QualityTier`'s 3→5 extension, a named exception, not a quiet break**: [17_ZERO_REWRITE_POLICY.md](../17_ZERO_REWRITE_POLICY.md) treats union-widening as additive by default, but every existing exhaustive `switch`/lookup over the old 3-value union (`assetQuality.ts`'s `TIER_OPTIONS`, `uniforms.ts`'s `TIER_TO_NUMBER`) needed real new entries, not just a passive pass-through — TypeScript's exhaustiveness checking caught both call sites immediately, which is exactly the safety net this policy exists to provide. Justified because this sprint's brief named all 5 tiers explicitly ("Support Ultra, High, Medium, Low, Minimal, Automatic") — an explicit user instruction, the one category [17_ZERO_REWRITE_POLICY.md](../17_ZERO_REWRITE_POLICY.md) always allows to override a frozen contract.

**Every runtime metric has exactly one producer, enforced structurally**: `runtimeProfiler.ts`'s `PerformanceSnapshot` is `Object.freeze()`'d at construction, not just documented as "don't mutate this" — a consumer that tries throws in strict mode. `recordPerformanceSnapshot` is the sole writer to the `latestSnapshot` bridge store; `evaluateAdaptiveQuality`, `checkGpuBudget`, and `DevPanel` all *read* it, none write back. This is the same one-producer-many-consumers shape the EventBus and every prior bridge store already established, applied here to a data type (a full snapshot object) rather than a scalar for the first time.

**One-directionality upheld, checked against the actual import graph**: `engine/performance/` imports nothing from `engine/materials`/`engine/shaders`. `qualityPolicy.ts`'s output flows one-directionally *into* `CupScene.tsx`/`CupCanvas.tsx`, which read `resolveQualityPolicy(tier)` and apply it to `dpr`, `shadow-mapSize`, and bloom — the Performance Manager never reaches into a scene object to mutate it directly, matching [15_ARCHITECTURE_FREEZE.md](../15_ARCHITECTURE_FREEZE.md)'s rule.

**A real, serious gap found by re-reading the sprint's own foundation, not invented busywork**: Sprint 2.1 built `tier`/`sampleFrame` and wired `DevPanelStatsCollector` to call `sampleFrame` every ~500ms — but `DevPanelStatsCollector` is dev-only (`NODE_ENV !== "production"`). Nothing fed the Performance Manager in a production build, meaning adaptive quality — built specifically to protect struggling-device sessions — could never have run on exactly the sessions it exists to protect. `PerformanceSampler.tsx` closes this for real: mounted unconditionally in `CupScene`, not gated. This was caught by tracing the actual call graph from `evaluateAdaptiveQuality` backward to its only caller, not by assumption.

## Performance review

**Asymmetric hysteresis, a deliberate evolution stated as such**: `adaptiveQuality.ts` steps down fast (3 consecutive samples below 45 FPS, ~1.5s) and up slow (10 consecutive samples at/above 55 FPS, ~5s). This changes [14_PERFORMANCE_STRATEGY.md](../14_PERFORMANCE_STRATEGY.md)'s original Sprint-1-era "never auto-step-up mid-session" rule — the change is documented in both the code's own comments and the doc, not silently reversed. The asymmetry is what actually prevents thrashing (a session hovering right at the threshold can't flip back and forth every 1.5s), rather than forbidding recovery outright.

**"Scale, don't disable" applied literally, checked field-by-field**: `qualityPolicy.ts`'s 5-tier table has exactly one boolean-off transition (`bloomEnabled: false`, `minimal` tier only) — DPR, shadow map size, bloom intensity multiplier, environment resolution, and particle budget all scale continuously across every tier instead. Verified by reading the table top to bottom, the same verification discipline Sprint 2.4's review applied to uniform ownership.

**Real-browser verification, not just unit tests**: 11 unit tests already covered `evaluateAdaptiveQuality`'s hysteresis edge cases in isolation, but this sprint's actual brief is about a system that runs continuously in a live scene — so a headless-Chrome CPU-throttle stress test was built (raw CDP over Node's built-in `WebSocket`, no new dependency added for one verification script) against the real dev server. Result: under 25x CPU throttling, the live tier stepped `ultra → high → medium → low → minimal`, one tier at a time, over ~13 seconds — consistent with the 3-sample/~1.5s downgrade cadence given real sampling jitter. Removing the throttle produced exactly one recovery step (`minimal → low`) within an 8-second window, consistent with the 10-sample/~5s upgrade cadence. This is the single most important verification this sprint could do, and it passed against real, not mocked, frame timing.

**No regression in the unthrottled path**: baseline (no throttle) samples held at a steady 120 FPS in the headless SwiftShader renderer, with the tier climbing `high → ultra` during the baseline window itself — the upgrade path firing correctly in a genuinely idle scene, not just theoretically present.

## Memory review

**Honest, indirect measurement — the same pattern as every prior sprint's memory-adjacent work**: no reliable cross-browser API measures actual heap/GPU memory (the same limitation Sprint 2.2's count-based LRU caps and Sprint 2.4's GPU-memory omission both already documented). `memoryPressure.ts` combines two already-real signals — `resource:evicted` rate (≥5 within a 10s window) and a concurrent `performance:degraded` streak — into one derived `memory:pressure` heuristic. Either signal alone is weak (a burst of evictions during a fast, high-FPS customizer session isn't memory pressure; one slow frame from a GC pause isn't either); both together, in the same window, is a real if still imperfect proxy. `resetMemoryPressureState`/the `alreadyReported` latch prevent duplicate reports for the same sustained streak.

## GPU review

**Budget checks against [14_PERFORMANCE_STRATEGY.md](../14_PERFORMANCE_STRATEGY.md)'s already-decided numbers, not new ones invented this sprint**: `gpuBudget.ts`'s `DRAW_CALL_BUDGET = 100` and `TRIANGLE_BUDGET = 55_000` (the hero object's 50k budget plus headroom for secondary objects) are read directly from the existing budget table. Draw calls are checked as the primary signal per that doc's own reasoning ("mobile GPU bottlenecks are frequently CPU-side draw-call submission overhead... this ceiling matters more than triangle count"). `checkGpuBudget` emits `gpu:budget-warning` only on the transition into over-budget, not on every sample while it stays over budget — required a real fix during testing (see Retrospective) once the crossing-detection state leaked across test cases.

**Scene totals, not per-object**: `gl.info` only reports scene-wide totals, so the triangle check is a coarser approximation of [14_PERFORMANCE_STRATEGY.md](../14_PERFORMANCE_STRATEGY.md)'s per-object budgets (hero <50k, secondary <500 each) than a true per-object breakdown would be — stated honestly in the code's own comment rather than implied to be more precise than it is.

## Accessibility review

No interactive surface changed this sprint. `PerformanceSampler`'s `useFrame` subscription correctly reflects R3F's actual render rate under `frameloop="demand"` (reduced motion) rather than an unconditional `requestAnimationFrame` loop, so it samples less often — not incorrectly — when reduced motion is active, matching the established pattern from every prior sprint's `useFrame`-vs-raw-rAF choice. `useSmoothedValue`'s damped bloom transition is explicitly skipped under reduced motion (`CupScene.tsx` reads the raw target directly rather than the smoothed value) — the same "disable outright, don't downgrade" motion policy applied everywhere else in this project, not a new carve-out invented for this sprint.

## Creative Director Review

**Delivered, correctly scoped, and honestly small**: bloom intensity damps toward its tier-driven target (`useSmoothedValue`, `THREE.MathUtils.damp` — the exact technique `CameraRig.tsx` established in Sprint 2.1, reused rather than reinvented) instead of snapping the instant a tier changes. This is the one parameter in the quality policy cheap enough to interpolate continuously — shadow map resolution is a discrete texture size that genuinely can't be animated between values without rendering at intermediate resolutions, which isn't practical, so it still snaps. Framed honestly per this sprint's own brief ("smoother transitions between quality tiers... less visible popping," not a new visual flourish): the improvement is real and verified (the stress test's throttled/recovery trace shows the tier stepping while bloom fades rather than pops), but it is a UX-smoothness win for a real class of users on struggling devices, not a headline visual moment. Scored accordingly — not inflated to match the visual weight of Sprint 2.3's material polish or Sprint 2.4's steam shader.

## Retrospective

### Technical debt

- `uQualityTier` (published since Sprint 2.4) still has zero in-shader consumers — this sprint's `qualityPolicy.ts` governs scene-level parameters (DPR, shadow map, bloom, environment resolution), not per-fragment shader branching. Wiring real tier-based GLSL branching (e.g. skipping a noise sample at `minimal`) remains a real, not-yet-taken opportunity, flagged again from Sprint 2.4's review rather than silently dropped.
- `steamQuality`/`coffeePhysicsQuality` fields exist on `QualityPolicy` (typed `"placeholder" | "full"` / `"off" | "full"`) with no real consumer yet — placeholders for Milestones 2/3's eventual final effects, matching this sprint's own "Future Steam quality, Future Coffee Physics quality" brief line. Same category as Sprint 2.3's `glass`/`metal` materials: cheap, typed, zero current cost, worth revisiting once those effects exist.

### Architectural observations

- The `gpuBudget.ts` test-isolation bug (module-level `drawCallsOverBudget`/`trianglesOverBudget` booleans persisting across test cases within the same file, since Vitest doesn't reset module state between tests by default) caused 2 of 5 tests to fail with stale crossing-state. Fixed by exporting `resetGpuBudgetState()` and calling it in a `beforeEach` — the same test-isolation discipline this project has hit before with module-level singletons, worth remembering as a default pattern whenever a new module keeps crossing-detection or other latch state at module scope.
- Three real `react-hooks/purity`/`react-hooks/refs` violations were found and fixed this sprint (`PerformanceSampler.tsx`, `useSmoothedValue.ts`, `DevDiagnosticsProbe.tsx`'s compile-time measurement) — each a call to `performance.now()` or a ref mutation happening during render/`useMemo` instead of inside `useEffect`/`useFrame`. Fixed by following Sprint 2.1's `useGestureRecognizer.ts` precedent (move the impure operation into an effect) rather than expanding `eslint.config.mjs`'s scope-off list — the fourth sprint in a row this exact fix pattern has recurred, which suggests it's now a reliable heuristic for this codebase's React-Compiler-era lint rules rather than a one-off.
- **A real verification-methodology finding, worth recording for future browser-based scripts**: the first CPU-throttle stress test run hung indefinitely with zero output. Root cause: this machine's Chrome profile has a pre-installed extension (Google Hangouts) whose `background_page` CDP target sorts ahead of the actual page target in `/json/list` — a script that naively takes `targets[0]` attaches to a target that never fires `Page.loadEventFired`, hanging forever with no error. Fixed by filtering for `type === "page"` explicitly, plus a hard timeout wrapped around the load-event wait so a future instance of this class of bug fails loudly instead of hanging silently. Worth carrying forward as a standing rule for any future CDP-based verification script in this project, not just this sprint's.

### Possible improvements

- `PerformanceSampler`'s ~500ms sampling cadence is a fixed constant, inherited unchanged from Sprint 2.1's dev-stats collector. Nothing this sprint made that cadence itself adaptive (e.g. sampling faster while actively degrading) — a reasonable future refinement, not attempted since the brief didn't call for it and the existing cadence is already what the hysteresis constants (3/10 samples) were tuned against.
- `memoryPressure.ts`'s ≥5-evictions/10s threshold is a first real number, not empirically tuned against an actual memory-constrained device — same honest caveat as [14_PERFORMANCE_STRATEGY.md](../14_PERFORMANCE_STRATEGY.md)'s count-based cache caps already carry.

## Sign-off

`git status` confirms every change this sprint is real, working, tested implementation — 30 new tests, all passing (146 total), verified against `tsc`/`eslint`/`build`, and — the sprint's most important verification — a real-browser CPU-throttle stress test confirming the adaptive quality tier actually steps down and recovers under genuinely degraded and then restored frame rates, not just in isolated unit tests. Waiting for approval before Sprint 2.6 (Integration & QA) begins.
