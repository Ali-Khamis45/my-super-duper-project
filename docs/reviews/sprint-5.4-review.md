# Sprint 5.4 — Inventory & Stock Management: Review

The Inventory bounded context, real end to end: `InventoryItem`/`InventoryReservation`/`InventoryTransaction` ([30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md)), full CQRS command/query set, EF Core migrations against a real PostgreSQL database, a real, direct (non-outbox) integration point with the `Order` lifecycle ([31_COMMERCE_ENGINEERING_CONTRACTS.md](../31_COMMERCE_ENGINEERING_CONTRACTS.md)) — plus a new `/admin/inventory` area (dashboard, low-stock indicators, restock/adjust/mark-availability actions, a reservation viewer, per-item transaction history), the second real area the `Staff` role reaches. Verified against a real PostgreSQL database and a real browser (Playwright) — not mocks. Five real bugs were found and fixed via this verification, detailed below.

**Scale**: Backend — 3 new aggregates/entities (`InventoryItem`, `InventoryReservation` — both real `AggregateRoot`s; `InventoryTransaction` — a plain `Entity`, append-only), 3 value objects (`Quantity`, `StockLevel`, `LowStockPolicy`), 8 domain exceptions, 12 domain events, 1 internal coordination service (`IInventoryReservationCoordinator`, deliberately not a set of public MediatR commands — see its own doc comment), 12 CQRS commands/queries, 3 EF Core configurations, 3 repositories, 1 migration (`AddInventory`), 1 seeder, 1 endpoint-group file (9 routes, all under `/admin/inventory`), 1 additive cross-context repository method (`IOrderRepository.GetOrderNumbersByIdsAsync`), 42 new Domain tests + 7 new Application tests (the coordinator) + 17 new Integration tests (against a real Testcontainers Postgres) — **234 backend tests passing, zero regressions** (up from Sprint 5.3's 172). Frontend — 1 API client file (`lib/inventory-client.ts`), 1 new feature directory (`features/admin/inventory/` — 6 hooks, 8 components), 3 new routes (`/admin/inventory`, `/admin/inventory/[id]`, `/admin/inventory/reservations`), 1 new guard hook (`useRequireViewInventory`), 4 new `AppEvent` union members (`inventory:restocked`/`-adjusted`/`-marked-out-of-stock`/`-marked-available`), 1 new permanent e2e spec (`admin-inventory.spec.ts` — 10 tests, every one independently verified passing). 302 pre-existing Vitest tests unaffected (this sprint added no new ones — every real new behavior is either pure CQRS/domain logic already covered by the 234 backend tests, or UI interaction covered by the new e2e spec; the same "no `.test.tsx` files, Playwright covers UI" convention Sprint 5.3's own review already established). `tsc`/`eslint`/`dotnet build`/`next build` clean throughout.

## Architecture review

**DDD's aggregate boundary held, with one deliberate, reasoned addition beyond the frozen sketch**: [30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md)'s Phase 0 sketch specified one `InventoryItem` aggregate root. Real implementation needed a second real aggregate, `InventoryReservation` — a reservation has its own independent lifecycle (`Consume`/`Release`/`Expire`, each individually invocable, e.g. a standalone admin "expire this stuck hold" action), which only a real `AggregateRoot` gets durable domain-event capture for through the existing, proven, zero-additional-plumbing `DomainEventsToOutboxInterceptor`. `InventoryTransaction` (the ledger row) stays a plain `Entity` — it never has independent behavior after creation, so promoting it to a third aggregate would have been unearned indirection.

**No Redis-backed reservation was built**, despite [29_COMMERCE_ARCHITECTURE_FREEZE.md](../29_COMMERCE_ARCHITECTURE_FREEZE.md) scenario 1 sketching exactly that. A `grep` across the whole backend during this sprint's own Phase 0 audit confirmed Redis (provisioned in `docker-compose.yml` since Sprint 5.0) has never been consumed by any real code in three prior sprints — building the *first* Redis integration in this project for one feature, when the real brief itself wants a durable, queryable admin "Reservation viewer" with real history, was a worse trade than a real Postgres table with a real `ExpiresAtUtc` column. Reservations expire *lazily* — reclaimed the moment another request needs that same ingredient's stock (`IInventoryReservationCoordinator.ReserveForOrderAsync`'s own pass-1 sweep), not via a scheduled background job — this project has no `BackgroundService`/Hangfire-style worker anywhere yet, and introducing the first one just for this would have been a bigger architectural addition than the brief asked for. The DDD model doc has been updated with the full, honest deviation list rather than silently left standing.

**The real integration point with Ordering is a direct, same-transaction call, never the outbox.** `IInventoryReservationCoordinator` is injected straight into `CreateOrderFromCartCommandHandler`/`CancelOrderCommandHandler`/`PayOrderCommandHandler`/`FailOrderCommandHandler` and called synchronously — not a nested MediatR `Send()` (which would trigger a second `SaveChangesAsync`, splitting "create the order" and "reserve its stock" into two separate transactions), and not a subscription to the `OrderSubmitted`/`OrderPaid`/etc. outbox events those handlers already raise (which would only be *eventually* consistent — wrong for "does this order actually have the stock it needs," which has to be answered before the order is allowed to exist at all). [32_COMMERCE_EVENT_CATALOG.md](../32_COMMERCE_EVENT_CATALOG.md) has been updated to make this explicit, since its own worked-example diagram originally implied the opposite flow.

**`InventoryAdjustment`/`InventoryTransaction`/`InventorySnapshot`, three concepts the brief names separately, map onto one real ledger mechanism** rather than three overlapping ones: `InventoryTransaction` is one append-only table, distinguished by an `InventoryReason` enum, with a `BalanceAfter` column serving as the brief's own named "snapshot" (a running balance captured on every entry, not a separately-scheduled snapshot table with no real consumer of "the balance at an arbitrary point in time"). The same discipline Sprint 5.3 already applied to `OrderAudit`/`OrderTimeline`.

## DDD review

Every invariant is enforced on the aggregate, never in a handler: `InventoryItem.Reserve` rejects a request exceeding `AvailableQuantity` (`InsufficientStockException`, raised alongside a real `InventoryReservationFailedEvent` on the exception path); `StockLevel.Create`/`.Subtract` reject a negative result (`NegativeStockException`) at the value-object level, so no code path — not `Consume`, not `Adjust`, not a future caller nobody's written yet — can construct an `InventoryItem` with negative stock even if it tried; `InventoryReservation.Consume`/`Release`/`Expire` each call `EnsureActive()` and reject a transition from any other status (`InvalidReservationStatusException`) — verified by dedicated tests for every legal and illegal transition, not spot-checked on one or two.

Domain events are raised from the aggregate method that causes them, never reconstructed after the fact: confirmed live, every event this sprint's code can raise was observed landing in the real `outbox_messages` table during manual verification (`InventoryItemCreatedEvent` ×9 from seeding, `InventoryReservationCreatedEvent`/`InventoryReservedEvent`/`InventoryConsumedEvent` from a real paid order, `InventoryReleasedEvent` from a real cancellation, `InventoryRestockedEvent`/`InventoryAdjustedEvent`/`InventoryOutOfStockEvent`/`InventoryBackInStockEvent` from real admin actions) — the same generic `DomainEventsToOutboxInterceptor` proven a fourth time now, with zero additional plumbing, across Identity, Catalog, Ordering, and now Inventory.

**The real reservation-atomicity guarantee, stress-tested, not just asserted**: `IInventoryReservationCoordinator.ReserveForOrderAsync` validates every requested ingredient's availability in a full pass *before* mutating any of them, and only reserves after every check has passed. A dedicated Application-layer test (`ReserveForOrderAsync_OneIngredientInsufficientAmongSeveral_ThrowsWithoutReservingAnyOfThem`) locks this in directly: a two-ingredient request where the second ingredient can't be covered leaves the *first* ingredient's `InventoryItem` — which alone had plenty of stock — completely untouched. A naive "reserve as you go" loop would have mutated it before reaching the failing ingredient, and since `UnitOfWorkBehavior` still calls `SaveChangesAsync` on the exception path (by design, for the refresh-token-reuse scenario Sprint 5.1 needs), that partial reservation would have been silently persisted despite the overall command reporting failure. Verified live too: a real order request for 100 units of foam against 25 available returned a real `409`, and a direct query confirmed foam's `availableQuantity` was untouched at 25, not partially decremented.

## Concurrency review

*(The brief's own explicit review category — Inventory is this project's first bounded context where two genuinely simultaneous requests can legitimately compete for the exact same finite resource, distinct from Ordering's own "pay this one order twice" race.)*

**Oversell prevention, verified under a real race, not just configured.** Two truly concurrent `POST /api/v1/orders` requests, each wanting 10 of the 15 available units of milk (so both together exceed what's available, but neither alone does — the shape of race that would succeed if both requests read the same stale snapshot): fired via genuinely parallel curl processes, not sequential calls. Result: one `201 Created`, one real `409 insufficient-stock`, and the final `availableQuantity` was exactly `5` (`15 - 10`) — never negative, never double-reserved, never silently both-succeeded. This is the same xmin-backed optimistic-concurrency protection every prior aggregate in this project relies on (`DbUpdateConcurrencyException` → `409`, `GlobalExceptionHandler`), now proven under real inventory contention specifically.

**The lazy-expiry sweep's own concurrency safety**: two concurrent requests both trying to reclaim the same expired reservation for the same `InventoryItem` can't both succeed — whichever's `SaveChangesAsync` commits second hits the same xmin conflict any other concurrent write to that row would, surfaced as the same real `409`. No special-cased locking was needed; the general mechanism already covers this specific new caller of it.

## Database review

One migration (`AddInventory`) — three new tables (`inventory_items`, `inventory_reservations`, `inventory_transactions`), generated and applied against a real PostgreSQL instance, with real indexes for every real query pattern this sprint's own repository code actually uses: a unique index on `inventory_items.ingredient_id` (the "one `InventoryItem` per `Ingredient`" invariant, enforced at the database level, not just application logic), a status index on both `inventory_items`/`inventory_reservations`, a composite `(inventory_item_id, status, expires_at_utc)` index backing the lazy-expiry sweep's own lookup, and `order_id`/`occurred_at_utc` indexes on `inventory_transactions` for the admin history view's real filters.

**A real, live-found bug closes a friction Sprint 5.3's own review left unresolved and explicitly flagged**: that review's Database section named an unexplained `dotnet ef database update` wrong-port connection issue as "worth a dedicated investigation before Sprint 5.4 needs its own migrations" — this sprint needed one, and the root cause was found: `DesignTimeDbContextFactory`'s hardcoded connection string had no `Port=` at all, defaulting to Npgsql's implicit `5432`, while `docker-compose.yml` maps this project's own Postgres to host port `5540` (avoiding a collision with other local projects' Postgres containers on the default port). `dotnet ef` was silently connecting to a *different* project's database and failing authentication there — not a mystery once traced, just never traced before. Fixed with an explicit `Port=5540`; verified by successfully generating and applying this sprint's own migration against the real intended database, and confirmed via a direct `psql` inspection of the resulting schema.

Optimistic concurrency (`xmin`-backed `RowVersion`) is wired for both `InventoryItem` and `InventoryReservation`, the same pattern every prior aggregate uses, and **verified live under a genuine race** (see Concurrency review, above) — not just configured and assumed correct.

## Performance review

`GetInventoryQuery`/`LowStockReportQuery`/`OutOfStockProductsQuery`/`GetInventoryDashboardQuery` all load the full ingredient set once per request (9 rows) into an in-memory dictionary for display-name resolution, never one query per row — the same N+1-avoidance discipline `CreateOrderFromCartCommandHandler`'s own `ingredientsByCode` pattern already established in Sprint 5.3. `GetInventoryDashboardQuery` uses a single grouped `GROUP BY` query for its real counts (`IInventoryItemRepository.GetStatusCountsAsync`), not three separate paged calls run just to read their `TotalCount`.

**A real, live-found EF Core query-translation bug, the same class of "looked correct, wasn't" finding Sprint 5.2/5.3's own reviews already caught variants of**: `GetInventoryDashboardQuery` 500'd on first live verification — `InventoryItemRepository.GetPagedAsync`'s `OrderBy(i => i.StockLevel.Value)` (member access on `StockLevel`, a `HasConversion`-mapped value-object property) failed to translate, even though the identical property translates fine in a `Where` equality check. Fixed by ordering on the VO property itself (`OrderBy(i => i.StockLevel)`) rather than its `.Value` member — letting EF apply the conversion's own `ToProvider` function directly, the correct, standard usage pattern for a value converter. Verified live: the dashboard endpoint returns real, internally-consistent grouped counts.

## API review

Every endpoint in the real, implemented Inventory surface is live at its documented path under `/api/v1/admin/inventory/`, RFC 9457 Problem Details for every error case (verified directly, including the new `InsufficientStockException`/`InventoryItemNotFoundException`/`InventoryReservationNotFoundException`/`InvalidReservationStatusException`/`InventoryItemAlreadyExistsException` mappings), and [37_API_STABILITY_POLICY.md](../37_API_STABILITY_POLICY.md) held with zero Sprint 5.1/5.2/5.3 contracts touched. Permission coverage checked exhaustively: every read endpoint requires `Permission.ViewInventory`, every mutating endpoint requires `Permission.AdjustInventory`, both seeded to `Staff` and `Admin` since this sprint's own `IdentitySeeder` addition — confirmed by grepping every `MapGet`/`MapPost`/`MapPut` registration, and confirmed live via a real `403` for a customer-role account and a real `200` for staff.

**A real, live-found DTO wire-format bug, caught before any real frontend consumer shipped against the wrong contract**: `InventoryStatus`/`InventoryReason` have multi-word enum members (`LowStock`, `OutOfStock`, `OrderConsumption`, `ManualAdjustment`) that would have collapsed to unreadable `"lowstock"`/`"outofstock"`/`"orderconsumption"`/`"manualadjustment"` under the exact `ToString().ToLowerInvariant()` convention `OrderStatus` already uses safely — safely only because every `OrderStatus` member happens to be a single word, a precondition this sprint's own review confirmed nobody had actually checked generalizes. Fixed with a real, explicit kebab-case mapping (`InventoryMappingExtensions.ToApiString`) before the admin frontend was built against it, and the API-side query-param parsing (`ParseStatus`/`ParseReason`) was written to accept that same kebab-case format back, verified by a real integration test round-tripping the API's own output as a filter input.

**A real DTO-completeness gap, found by the e2e suite specifically (not manual curl testing, which never had a reason to look for it)**: `InventoryReservationDto` originally carried only the raw `OrderId` Guid — correct data, but not what a real member of staff actually works with (an order's human-readable number, `"CS-000042"`, the same identifier `/admin/orders`'s own search already keys on). The Reservation Viewer literally rendered an opaque UUID in its Order column. Fixed additively: `IOrderRepository.GetOrderNumbersByIdsAsync` (a real, deliberate cross-bounded-context repository dependency — Inventory's query handlers reading directly from Ordering's own repository, the same precedent `CreateOrderFromCartCommandHandler` already set reading Catalog's repositories directly), one batched lookup per query, never one query per reservation row. `InventoryReservationDto.OrderNumber` is additive, `OrderId` is untouched — no existing consumer's contract changed.

## Creative review

The Inventory pages match `AdminNav`'s already-established plainer utility chrome (`Card`/`Badge`/`Table`, no glass/glow treatment) rather than introducing a new visual system — this sprint's brief was "real stock management," not "redesign." `InventoryStatusBadge`'s status→variant mapping (`available`→default, `low-stock`→secondary, `out-of-stock`→destructive) is a small, real design decision, distinct from `ReservationStatusBadge`'s own mapping — an item's stock health and one hold's own lifecycle are genuinely different concepts, not one badge doing double duty. The dashboard's low-stock/out-of-stock counts render in a visually distinct (destructive-colored) treatment only when non-zero, so a healthy inventory state doesn't draw attention to numbers that don't need it.

## Regression review

**302 pre-existing Vitest unit tests, unchanged and passing — zero regressions.** The full pre-existing Playwright e2e suite was not re-run in its entirety this sprint (a full-suite run's own real environmental cost was already documented at length in Sprint 5.3's own Regression review — a multi-hour dev machine with several unrelated Docker containers running concurrently), but every test file this sprint's own backend changes could plausibly affect (`orders.spec.ts`, `admin-orders.spec.ts`) touches code this sprint only *extended* additively (new constructor parameters on existing command handlers, no removed/renamed behavior) — the 38 backend Integration tests covering the full Order lifecycle (including the pre-existing Ordering suite, unmodified) passing at 100% is the direct evidence those extensions didn't break anything, backend-side, which is the layer this sprint's changes actually touched.

**The new `admin-inventory.spec.ts` (10 tests) is real, permanent regression coverage — not a one-off manual script.** Every test passed against the real dev stack (real Postgres, real backend, real browser) once this sprint's own two e2e-authoring bugs (below) were fixed; individual re-runs during that fixing process also hit the same rate-limiter/dev-machine-load flakiness Sprint 5.3's own Regression review already documented and accepted for this project's e2e suite in general (one login-step timeout mid-run, cleanly passing in isolation immediately after) — not a new class of problem, the same one, on the same machine.

**A new environmental friction, distinct from Sprint 5.3's own rate-limiter/WebGL-contention findings**: this dev machine has a Windows-level TCP port exclusion range (`2913`–`3012`, confirmed via `netsh interface ipv4 show excludedportrange`) that happens to include port `3000` — `playwright.config.ts`'s own default dev-server port — causing `EACCES: permission denied` on every `next dev` startup attempt during this sprint's own verification, unrelated to anything this sprint shipped (the exclusion range predates this session). Worked around locally by running the dev server on port `4100` for this sprint's own manual e2e verification, which in turn required a matching `Cors:FrontendOrigin` override on the backend (`Program.cs`'s CORS policy is hardcoded to `localhost:3000` by default) — both overrides were local-only and are not part of this sprint's committed changes. Flagged here, not silently worked around forever: `playwright.config.ts`'s committed default (port `3000`) is unaffected and will work correctly on any machine without this specific Windows port-exclusion quirk.

## Lessons learned

Every one of this sprint's real findings, in the order found:

1. `DesignTimeDbContextFactory`'s connection string had no explicit `Port=5540`, silently connecting `dotnet ef` to a *different* local project's Postgres instance on the implicit default port — the exact friction Sprint 5.3's own review flagged as unresolved and worth investigating before this sprint needed its own migrations (Database review, above). Found immediately on this sprint's first `dotnet ef database update` attempt.
2. `GetInventoryDashboardQuery` 500'd — `OrderBy(i => i.StockLevel.Value)` (member access on a `HasConversion`-mapped VO property) doesn't translate, even though the same property translates fine in a `Where` equality check (Performance review, above). Found via live testing, not a design review — the exact kind of "looked correct, compiled clean, broke at runtime" finding this project's review discipline exists to catch a fourth time now (after `Email`, `Price`/`Sku`, `OrderTotals`).
3. `InventoryStatus`/`InventoryReason`'s multi-word enum members would have serialized as unreadable, un-parseable strings under the exact convention `OrderStatus` uses safely — a precondition (every enum member is one word) nobody had verified actually holds for the new enums (API review, above). Found during this sprint's own live verification, before any real frontend consumer shipped against the wrong contract.
4. `useInventoryMutations.ts`'s `invalidateAndCache` never invalidated the `["admin-inventory-history"]` query key — TanStack Query's `invalidateQueries` matches by query-key *array* prefix, not string prefix, so `["admin-inventory-history", ...]` was never touched by an `invalidateQueries({ queryKey: ["admin-inventory"] })` call despite the visually-similar key names. Every restock/adjust/mark action silently left the "Recent activity" panel showing stale data until a full page reload. Found by the new e2e spec's own adversarial assertion design (checking for the specific rendered delta text, e.g. `"+7 → 48"`, not just the ever-present "Restock" card heading, which would have passed even with the bug present) — a real example of writing a test specific enough to actually catch a bug, not just exercise the happy path.
5. `InventoryReservationDto` carried only a raw `OrderId` Guid — technically correct, but the Reservation Viewer rendered that Guid directly, not the human-readable order number staff would actually recognize (API review, above). Found by the e2e spec's own end-to-end test asserting the real order number was visible on the page — a manual curl-based check would never have surfaced this, since curl output shows every field equally, with no "is this actually usable by a human" signal a rendered page provides for free.

**Two additional issues were found and fixed in the *e2e test file itself*, not the shipped feature** — worth naming separately since they could otherwise read as feature bugs: `admin-inventory.spec.ts` originally registered a fresh account per test (9 tests × 1 register each), which reliably exhausted `AuthPolicy`'s real 10-requests/minute rate limiter partway through a run — refactored to `test.describe.serial` with one shared staff login (`beforeAll`), reused across every staff-only test, the same "cache shared identities" reasoning `OrderEndpointsTests.cs`'s own `GetOrCreateAsync` already established on the backend integration-test side of this identical problem. And a search-then-click race (filling the search box and immediately clicking "View" before the debounced query had actually filtered the table down) caused a Playwright strict-mode violation resolving to all 9 unfiltered rows — fixed by waiting for the filtered result count before clicking, the same "wait for the real state, don't assume timing" discipline this project's own review process already applies to application code. Relatedly, the end-to-end test's own first draft assumed the `/customize` 3D flow's default "Add to Cart" carries real ingredients — it doesn't (no ingredient is added without an explicit customizer drag-and-drop interaction) — fixed by creating the test order via a direct API call instead of automating an unrelated, fragile 3D interaction.

**Every one of this sprint's five shipped-feature findings was caught by live testing against the real running system, not code review** — the same pattern Sprint 5.1 through 5.3's own reviews already drew, now a fourth-time-confirmed argument for this project's phase ordering (build, then verify live, then dedicated adversarial pass) over trusting a design or a compile pass alone. Finding 5 specifically is also a real, concrete argument for e2e coverage's own distinct value over API-level testing alone — every backend integration test for this DTO passed the whole time, because the Guid *was* being returned correctly; only a rendered page made "correct but useless to a human" visible.

## Retrospective

What went well: the outbox pattern's generality paid off a fourth time — `InventoryItem`/`InventoryReservation` gained durable domain-event capture with zero additional plumbing, the same payoff proven three times before now proven a fourth. The deliberate decision to make `IInventoryReservationCoordinator` a direct, same-transaction call rather than a public MediatR command set was validated concretely, not just argued for in the abstract — the dedicated atomicity test (`ReserveForOrderAsync_OneIngredientInsufficientAmongSeveral_ThrowsWithoutReservingAnyOfThem`) and the live insufficient-stock repro both confirm the design actually delivers the "no phantom order on failure" guarantee it was built for. Closing out Sprint 5.3's own unresolved `dotnet ef` port mystery as a real side effect of this sprint's own migration work is a genuine example of the review discipline compounding — a flagged-but-deferred finding actually getting resolved rather than accumulating indefinitely.

What to carry forward: the EF Core value-converter lesson list is now five items long (`Email`, `Price`/`Sku`, `OrderTotals`'s constructor, `OrderTotals`'s shared-reference bug, and now `StockLevel`'s `OrderBy(...).Value` translation gap) — still worth the dedicated internal note in [41_BACKEND_DEVELOPMENT_STANDARDS.md](../41_BACKEND_DEVELOPMENT_STANDARDS.md) Sprint 5.3's own retrospective already recommended and this sprint didn't get to either. The kebab-case-vs-plain-lowercase DTO inconsistency between `InventoryStatus` and `OrderStatus` is a real, narrow API-design wrinkle worth a one-line callout in [41_BACKEND_DEVELOPMENT_STANDARDS.md](../41_BACKEND_DEVELOPMENT_STANDARDS.md)'s own DTO-mapping guidance ("check whether `ToString().ToLowerInvariant()` is actually safe for this specific enum's member names before reaching for it") so the next multi-word enum doesn't rediscover the same gap from scratch.

What's explicitly deferred, not forgotten: "bulk adjustments" (named in this sprint's own Phase 6 brief) — no backend batch-adjustment command was built, so no UI was built for it either, rather than shipping a client-side loop implying an atomicity guarantee the backend can't actually provide (see `features/admin/README.md`'s own "Known simplifications" note); a standalone cross-item inventory history/audit view (the per-item "Recent activity" panel covers the one real staff workflow this sprint identified — "why does this ingredient's balance look wrong" — without a second page, but `useInventoryHistoryQuery` already supports an unfiltered call if a real need for one surfaces); real-time inventory updates via SignalR (a second admin viewing the same item's page doesn't see another staff member's restock without a reload, the same limitation Sprint 5.3's own review already named for Orders). Payments, Coupons, and the "Administration Platform" scope (`ContentBlock`/`AuditLogEntry`/`Review`/Users) this project's own original roadmap sketch assigned to a future sprint numbered "5.4" remain entirely unbuilt — see [39_COMMERCE_IMPLEMENTATION_READINESS.md](../39_COMMERCE_IMPLEMENTATION_READINESS.md)'s own note reconciling that original sketch against what this sprint's real brief actually asked for.

Waiting for the user's review and explicit approval before Sprint 5.5 begins — not started automatically, per this project's established rhythm. Payments are explicitly not started, per this sprint's own brief.
