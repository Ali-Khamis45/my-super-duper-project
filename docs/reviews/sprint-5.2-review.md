# Sprint 5.2 — Product Platform: Review

The Catalog bounded context, real end to end: `Product`/`Category`/`Ingredient` aggregates ([30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md)), full CQRS command/query set, EF Core migrations against a real PostgreSQL database, PostgreSQL full-text search (weighted `tsvector`/GIN, trigram autocomplete, no Elasticsearch — [29_COMMERCE_ARCHITECTURE_FREEZE.md](../29_COMMERCE_ARCHITECTURE_FREEZE.md)), the full REST surface ([31_COMMERCE_ENGINEERING_CONTRACTS.md](../31_COMMERCE_ENGINEERING_CONTRACTS.md)) — plus real frontend integration replacing the static catalog as the live data source for `/menu`, `/customize`, `/concierge`, and a brand-new protected `/admin` area (products/categories/ingredients CRUD, this project's first permission-gated route) under an unmodified Zero Rewrite Policy. Verified against a real PostgreSQL database and a real browser (Playwright, three engines) — not mocks. Twelve real bugs were found and fixed via this verification, detailed below.

**Scale**: Backend — 3 new aggregates, ~13 value objects/enums, 10 domain exceptions, 11 domain events, ~20 CQRS commands/queries, 4 EF Core configurations, 3 repositories, 1 search service, 1 seeder, 1 migration, 5 endpoint-group files, 36 new Domain tests + 20 Application tests + 14 Integration tests (70 new backend tests total, on top of Sprint 5.1's 42 — 102 backend tests passing, zero regressions). Frontend — 5 API client files, 1 shared error-handling module, 2 mapping/icon-lookup modules per feature (menu, composer), 3 Zustand stores, 4 TanStack Query hooks, a full `/admin` feature (guard, nav, 3 CRUD areas, ~15 components), 19 new Vitest tests (299 total, zero regressions), 1 new permanent e2e spec (`admin.spec.ts`, 5 tests). `tsc`/`eslint`/`dotnet build` clean throughout.

## Architecture review

**DDD's aggregate boundaries held, with one genuine addition beyond the frozen sketch**: `Product`, `Category`, and `Ingredient` are three separate aggregate roots exactly as [30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md) specified — a `Product` references `CategoryId` by id, never an embedded `Category`. `IngredientCategory`, a lightweight reference entity (mirroring `Permission`'s role in Identity), was not named in the original sketch at all; it exists because the frontend's own `data/ingredients.ts` already drew a real distinction between "which named type" (foam, milk, syrup — 9 of them) and "which specific ingredient" (today 1:1, but not architecturally forced to stay that way) — the domain model just makes that existing distinction real.

**`IRepository<TAggregate, TId>` is implemented for real this sprint** — deferred at Sprint 5.1 as not yet earning its indirection for a two-aggregate Identity context, now validated by three aggregates sharing the exact same shape (`GetByIdAsync`, `Add`) with zero forcing or awkward fit. This is the kind of design question Sprint 5.1's own review said it would revisit honestly once there was real evidence either way — there was, and the deferred design held.

**One real, reasoned deviation from the frozen invariant sketch**: [30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md)'s original table described a `Product.IsActive` boolean for discontinuation. Real implementation needed a genuine three-state lifecycle (`Draft → Published ⇄ Archived`) — Draft/Published because "create it, then decide when it's customer-visible" is a real admin workflow the brief's own "Draft/Published, search, pagination, bulk actions" line asked for, and Archived-with-restoration because a boolean "discontinued" flag has no way back. `ProductStatus` (enum) replaced the sketched boolean; the DDD model doc has been updated to describe the real, implemented invariant rather than the sketch (see that doc's own Catalog section).

**Two backend-scoped gaps found and fixed during Phase 10's dedicated review, both examples of "implementation surfaces what a design sketch couldn't have known"**: `CreateIngredientCommand` accepted an `IngredientCategoryId` with no validation that it referred to a real row — no FluentValidation rule catches a syntactically-valid-but-nonexistent Guid, and there is deliberately no database foreign key either (`IngredientCategory` has no navigation configured, matching its "lightweight reference entity" design). Fixed by moving the existence check into the handler (`IngredientCategoryNotFoundException`), the same pattern `CreateProductCommandHandler` already used for `CategoryCode`. Separately, `DeleteProductCommand`'s hard-delete path raised no domain event at all — every other product-lifecycle transition does. Fixed by adding `Product.PrepareForDeletion()` (moving the Draft-only guard into the aggregate, where every other transition rule already lives) and a new `ProductDeletedEvent`.

## DDD review

Every invariant is enforced on the aggregate, never in a handler: `Price.Create` throws `InvalidPriceException` for a non-positive amount; `Product.Publish()`/`Archive()`/`Restore()` reject illegal transitions (`InvalidProductStatusTransitionException`); an `Archived` product rejects every other mutation (`ProductArchivedException`) until restored — verified directly via a `[Theory]` test enumerating every mutating method against an archived product, not spot-checked on one or two. Domain events are raised from the aggregate method that causes them, never reconstructed after the fact from a diff — confirmed live: every event this sprint's code can raise was observed landing in the real `outbox_messages` table during manual verification (`ProductCreatedEvent` ×16, `ProductUpdatedEvent` ×61, `ProductPublishedEvent` ×16, `ProductArchivedEvent`, `ProductRestoredEvent`, `ProductPriceChangedEvent`, `IngredientCreatedEvent` ×9, `IngredientUpdatedEvent`, `CategoryCreatedEvent` ×5, plus `CategoryUpdatedEvent` and `ProductDeletedEvent` confirmed separately once their code paths existed) — this is the same generic `DomainEventsToOutboxInterceptor` Sprint 5.1 built for `User`, now proven to generalize to a second bounded context with zero additional plumbing, exactly the payoff the outbox pattern's design promised.

Value objects stay immutable and self-validating: `Money`/`Price`/`Sku`/`ProductTag`/`NutritionFacts` all construct through a `Create` factory that throws on an invalid state, never a public setter. One real EF Core lesson applied from the start this sprint (not rediscovered): a value object whose constructor takes other value objects (`Price` wrapping two `Money` instances) cannot be constructor-bound by EF's owned-type materialization — needed a parameterless constructor + private setters, caught during migration generation, before it ever reached a running database.

## Performance review

**Real indexes for real query patterns, not assumed**: `products` has B-tree indexes on `CategoryId`/`Status`/`IsAvailable`/`IsFeatured` (every filter `GetProductsQuery`/`GetMenuQuery` actually uses) plus a unique index on `Sku`, a GIN index on the generated `search_vector` `tsvector` column, and a trigram GIN index (`gin_trgm_ops`) on `Name` — all confirmed present via the generated migration, not asserted from the configuration alone. **N+1 queries were specifically checked for and found clean**: `GetProductsQuery`/`GetMenuQuery` both load the full category set once (a handful of rows) and build an in-memory dictionary, never one query per product — the exact risk this sprint's own review checklist named.

**One real query-shape issue found and fixed**: every `Product` fetch loads two owned collections (`Variants`, `Images`) via a single JOIN, which EF Core flags on every query ("no `QuerySplittingBehavior` configured — can potentially result in slow query performance"). Live-verified as a real, recurring warning (present on every `/menu`/`/products/{id}` call), not theoretical. Fixed by explicitly configuring `QuerySplittingBehavior.SingleQuery` — the existing implicit default, made an informed choice rather than an unaddressed warning: both collections are small and bounded (a handful of variants/images per product, never the unbounded-child-table case the warning is really guarding against), so one round trip stays cheaper than `SplitQuery`'s multiple-query alternative. Verified live: the warning is gone from a fresh API run's logs after the fix, confirmed by triggering the same query that previously produced it.

The admin product list's new `ProductFilter.SearchTerm` (a plain `ILIKE` name search, added because the ranked `/search` endpoint can't be reused for an admin view that needs to see Drafts) was checked against `EXPLAIN` — Postgres correctly chooses a sequential scan over the trigram index at this catalog's size (14 rows), which is the right cost-based decision, not a missing-index bug; the index exists and would be used once row counts justify it.

No dedicated load testing this sprint (correctly out of scope — Sprint 5.6's job).

## Database review

The migration was generated and applied against a real PostgreSQL instance (not just compiled), and the seed data (`CatalogSeeder`) was verified live: 4 categories, 9 ingredients, 14 products, each traced verbatim from the frontend's own static data files rather than invented — `ProductVariant` price adjustments seeded at real `$0.00` (matching actual current frontend behavior), `ProductImage` seeded with zero rows (no real images exist to seed), `NutritionFacts` caffeine values from genuinely well-known typical figures with calories/sugar deliberately left `null` rather than fabricated. Optimistic concurrency (`xmin`-backed `RowVersion`, the same pattern Sprint 5.1 established for `User`) is wired for `Product`, and the previously-unmapped `DbUpdateConcurrencyException → 500` gap (a real finding from live API testing, not from a design review) is now a proper `409 Conflict`.

One known, accepted, low-severity gap, documented rather than silently left: `NutritionFacts` triggers an EF Core warning ("optional dependent using table sharing without any required non-shared column") — a real limitation for optional owned types when every field could be null simultaneously. Not currently reachable (every seeded product has a real non-null `CaffeineMg`), and fixing it would add complexity (a required discriminator column) for a case that can't happen with today's data — flagged honestly rather than fixed speculatively or left unmentioned.

## Search review

PostgreSQL full-text search, not Elasticsearch, per the frozen architecture decision — a `stored` generated `tsvector` column combining `name`/`tagline`/`description` with weights `'A'`/`'B'`/`'C'` respectively, so a name match ranks above a description-only match. **Ranking was verified with real data, not just unit-level assertions**: a live `psql ts_rank` query proved a genuine name match ("Chai Latte" for the query `"latte"`) outranks a description-only match ("Flat White," which only mentions "latte" in its description) by the expected margin — this exact finding is now locked in as a permanent regression assertion in `CatalogEndpointsTests.cs`. Prefix matching (`term:*` per real word, each term sanitized to alphanumerics before embedding — an unsanitized query containing `tsquery` syntax characters like `&`/`|`/`(` would otherwise be a real 500, not a graceful zero-result search) was verified against real multi-word queries. Autocomplete uses a separate trigram index path (`ILIKE 'prefix%'`), deliberately not routed through the ranked search — a tighter latency budget and simpler ranking need.

**One real query-correctness issue found and fixed**: the autocomplete query originally chained `.OrderBy(name).Select(name).Distinct().Take(n)` — EF Core warned this ordering could be silently erased by `Distinct()`, and while the specific case happened to work (the ordering key and the distinct/selected column were the same single column), the warning was real and the pattern fragile. Fixed by reordering to `.Select().Distinct().OrderBy().Take()`, which is unambiguous by construction rather than working by coincidence — verified: the warning is gone, and the regression test (`Autocomplete_MatchesNamePrefix`) still passes.

## Accessibility review

The admin area reuses this project's existing accessible primitives (`Label`/`Input`/`Select`/`Checkbox`/`Table`, all newly added via the `shadcn` CLI this sprint, matching this project's established tooling) rather than hand-rolled controls. One real a11y finding, in a *generated* file, not this sprint's own hand-written code: the shadcn-generated `Label` component (a generic `<label {...props}>` passthrough) fails `jsx-a11y/label-has-associated-control` because the lint rule can't trace `htmlFor` through a props spread — every real call site in this codebase supplies it correctly, verified by inspection, so the rule's flag is a true false positive on the component definition itself, not a real missing-association bug. Fixed with a single, explained `eslint-disable-next-line` rather than restructuring a generated component or leaving an unexplained suppression. The admin guard's three real states (`checking`/`unauthenticated`→redirect/`forbidden`→`AccessDenied`) each render distinct, real content — no layout flash between them beyond the same brief `aria-busy` placeholder pattern `AccountMenu` already established in Sprint 5.1.

## API review

Every endpoint in the real, implemented Catalog surface is live at its documented path under `/api/v1/`, RFC 9457 Problem Details for every error case (verified directly, including the new `IngredientCategoryNotFoundException`/`DbUpdateConcurrencyException` mappings), and [37_API_STABILITY_POLICY.md](../37_API_STABILITY_POLICY.md) held with zero Sprint 5.1 contracts touched — every extension this sprint made used one of that policy's own permitted mechanisms for real, not just in theory: additive DTO fields (`ProductSummaryDto.Description`, `IngredientDto.SortOrder` — both real gaps found by building the actual frontend/admin consumer, not spec-driven), new endpoints (`GET /api/v1/ingredient-categories`, needed once `CreateIngredientCommand.IngredientCategoryId` turned out to be otherwise undiscoverable through any existing route), and a new query parameter (`ProductFilter.SearchTerm`, additive and optional). No mechanism 5 (a new API version) was needed. Permission coverage was checked exhaustively, not spot-checked: every mutating Catalog endpoint requires `Permission.ManageProducts`; every read is `AllowAnonymous` — confirmed by grepping every `MapPost`/`MapPut`/`MapDelete`/`MapGet` registration, not by memory.

## Creative review

The admin area intentionally uses plainer chrome than the public marketing site (`AdminNav`'s bordered utility bar vs. `Navbar`'s floating glass pill) — a deliberate, real distinction most production admin panels draw, not an oversight or a lower design bar. The customer-facing `/menu`/`/customize`/`/concierge` pages are visually unchanged from Sprint 3.x's own Creative Director Review — this sprint's brief was "replace the data source," not "redesign the experience," and the real e2e regression suite (including reduced-motion and touch-target passes) confirms the visual/interaction layer held exactly as before. New states this sprint had to design for real, since the static-data era never needed them: `MenuLoadingState` (a card-shaped skeleton grid, so the grid's final layout never jumps once real data lands — deliberately not a spinner) and `MenuErrorState` (visually and functionally distinct from "no results," since a failed fetch needs "retry," not "try a different search").

## Regression review

**280 pre-existing Vitest unit tests, then 299 after this sprint's own 19 additions — zero regressions, zero modifications needed to any pre-existing test.** The full existing Playwright e2e suite (`menu`, `customizer`, `concierge`, `composer`, `cart` — 73 tests) was run against the live backend, not just against the old static data, and passes 100% on Chromium and Firefox, and 100% on WebKit outside a pre-existing rate-limiter interaction reproduced identically on Sprint 5.1's own untouched `auth.spec.ts` (see Lessons learned, below — confirmed not a Sprint 5.2 regression before being written off as environmental).

**The single largest regression risk this sprint carried, and how it was actually retired**: replacing `Drink.id`'s data source (static array → live backend) without breaking `cart-store`/`customizer-store`/`recommendationEngine`'s existing string-matching logic, and every test written against it. Resolved by deriving `Drink.id` client-side (`slugify(product.Name)`) rather than serializing the backend's real `Guid` — verified byte-identical to all 14 real seeded products' original static ids via a dedicated unit test (`mapProductToDrink.test.ts`), not just spot-checked. `data/drinks.ts`/`data/ingredients.ts` themselves were kept completely unmodified — used as-is by every pre-existing test and by every internal "resolve an already-known id back to display data" call site (`RecipeSummary`, `DrinkComparison`, `LayerStack`, etc.), which is safe precisely because the static and live data are verified identical, not because those call sites were left un-audited.

## Lessons learned

Every one of this sprint's twelve real findings, in the order found:

1. `Price`'s constructor (taking two other value objects) couldn't be EF-materialized without a parameterless constructor + private setters — caught during `dotnet ef migrations add`, before it ever ran against a database.
2. A self-caught placeholder: an early draft of `ProductRepository.ApplyFilter` referenced a nonexistent helper type — recognized as wrong before it was ever tested, rewritten as a real correlated `EXISTS` subquery.
3. `Season`/`Status`/`Temperature` all correctly lowercase on the wire except `Season`, missing one `.ToLowerInvariant()` call — found via live API testing (`GET /featured` returning `"AllYear"` instead of `"allyear"`), not code review.
4. `DbUpdateConcurrencyException` fell through to an unmapped `500` — found by code review of the exception-handling switch, fixed proactively to a `409`.
5. The autocomplete query's `OrderBy`-before-`Distinct` ordering ambiguity (Search review, above).
6. `ProductSummaryDto` missing `Description`, discovered only once the real frontend consumer (`DrinkDetailDialog`) was built and needed it for every item the `/menu` grid already renders.
7. `IngredientDto` missing `SortOrder`, discovered only once the real admin consumer needed to round-trip a value `UpdateIngredientCommand` requires on every call but nothing previously exposed.
8. A genuinely missing endpoint (`GET /api/v1/ingredient-categories`), discovered only once the admin ingredient editor needed a real Guid nothing else could supply.
9. `CreateIngredientCommand.IngredientCategoryId` had no existence validation and no database foreign key either (Architecture review, above).
10. `DeleteProductCommand`'s hard delete raised no domain event (Architecture review, above).
11. Every product query's `QuerySplittingBehavior` warning (Performance review, above).
12. A shadcn-generated `Label` component's false-positive a11y lint failure (Accessibility review, above).

**Half of these (6-10) were found only by building the real frontend/admin consumer, not by backend code review alone** — the same lesson Sprint 5.1's review drew from live verification catching bugs static analysis couldn't, extended here: a DTO or endpoint contract can look complete in isolation and still be missing exactly the field or route its first real caller needs. This is the concrete argument for this sprint's phase ordering (backend first, then a real frontend consumer, then a dedicated review pass) over building the whole backend surface speculatively complete before anything used it.

**A rate-limiter interaction worth naming, not fixing**: running this sprint's new `admin.spec.ts` (which registers several accounts) back-to-back with other registration-heavy specs can exhaust `AuthPolicy`'s 10-requests/minute ceiling within a single test run, producing failures that look like a bug but aren't — confirmed by reproducing the identical failure on Sprint 5.1's own unmodified `auth.spec.ts` in isolation. The correct fix is not weakening a real production rate limit for testing convenience; this is carried forward as a known, accepted friction for local/CI e2e runs that register many accounts in a tight loop, not a Sprint 5.2 defect.

## Retrospective

What went well: the Outbox pattern's generality paid off immediately — three new aggregates gained durable domain-event capture with zero additional plumbing, the exact payoff Sprint 5.1's design was betting on. The `IRepository<TAggregate, TId>` deferral from Sprint 5.1 was the right call to defer *and* the right call to implement now — three aggregates gave real evidence a two-aggregate context couldn't. Deriving `Drink.id` client-side rather than switching to the backend's `Guid` turned out to be the single highest-leverage design decision this sprint made for regression safety — it's the reason zero pre-existing tests needed modification despite the entire data layer underneath them changing.

What to carry forward: roughly half of this sprint's real bugs were only found by building the real consumer of a contract, not by reviewing the contract in isolation — a strong argument for keeping "backend, then real frontend integration, then dedicated review" as the phase order in every future sprint, rather than trying to make the backend "complete" before anything real uses it. The image-by-URL decision (no fake file-upload picker, because no blob storage exists in this architecture) is a real instance of this project's "no placeholder implementations" rule doing genuine work, not just being satisfied trivially.

What's explicitly deferred, not forgotten: a Redis read-through cache in front of catalog reads (no real justification at today's ~14-product scale; PostgreSQL's own indexes are the right answer until that changes); the Outbox dispatcher (still Sprint 5.3+, once `Order` gives it a real first consumer — unchanged from Sprint 5.1's own deferral); a featured-drinks read/write path end to end (`getFeatured`/`setFeatured` were both written, then deliberately removed once written, since neither has a real consumer yet — no featured section exists anywhere in the frontend; add both back together the same milestone one does); `IngredientCategory` growing a second ingredient per category (the domain model already supports it, nothing currently exercises it).

Waiting for the user's review and explicit approval before Sprint 5.3 (Ordering Platform) begins — not started automatically, per this project's established rhythm.
