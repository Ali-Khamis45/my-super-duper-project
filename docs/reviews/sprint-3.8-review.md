# Sprint 3.8 — Final Polish & Release Candidate: Review

The final sprint of Milestone 3. Not a features sprint — a complete implementation audit (Phase 0) followed by additive-only refinement across every implemented system, ending in a Release Candidate (RC1), not a public release. Zero engine rewrites; every fix landed through composition, configuration, preset values, or a locally-scoped, additive code change, checked against [17_ZERO_REWRITE_POLICY.md](../17_ZERO_REWRITE_POLICY.md) before being made.

Full Release Candidate artifact — Architecture Score, Performance Report, Accessibility Report, the complete 17-category Creative Director Review, Regression Report, Engine Health Report, Risk Register, Technical Debt Summary, Known Limitations, and Deployment Readiness Checklist — lives in [RC1_RELEASE_CANDIDATE_REPORT.md](../RC1_RELEASE_CANDIDATE_REPORT.md). This document is the sprint's own process narrative: what was audited, what was found, what was fixed, and why some real findings were deliberately left undone.

## Phase 0 — Project audit

Four parallel, read-only audits (Hero/Menu/Customizer; Composer/Physics/Concierge; Storytelling/Cart/Checkout; the whole `engine/` layer — every manager) — genuinely adversarial, not rubber-stamped, per this project's own established review discipline. Each audit was told explicitly: "nothing should be assumed correct because it already works." Combined, they surfaced ~40 concrete, file:line-referenced findings, several of them real bugs, not style nits:

- A real scoring bug in the AI Concierge's recommendation engine (three of six caffeine-preference branches used the wrong weight constant, silently under-weighting the most common preference, "regular," relative to "none"/"high").
- A real, measurable performance regression in `/story`'s scroll-driven scene: `chapterProgress` (updating on every GSAP scroll tick) was subscribed to unconditionally, re-rendering the entire 3D tree on every scroll frame for all 7 chapters even though only 2 ever use it.
- A real, near-identical performance bug in the Customizer: hovering any one swatch re-rendered all six `VariantSwatchGroup` sections, contradicting that component's own doc comment about per-category isolation.
- A latent material-cache bypass: Coffee and Foam's `materialOverrides` branch constructed one-off materials and re-ran a full shader recompile (`onBeforeCompile`) on every render instead of routing through the shared cache like every sibling part.
- A missing GPU-resource disposer on the logo texture cache — a real, if currently dormant, WebGL texture leak.
- The single highest-value engine finding: 5 of the shared shader uniform block's 8 fields (`uQualityTier`, `uThemeMode`/`uColorTheme`, `uResolution`, `uLightingIntensity`, `uIsInteracting`) had real, typed publisher functions with **zero call sites anywhere in production code** — frozen at module-load defaults since the file was written, despite its own doc comment claiming they were live.
- A genuine, confirmed visual bug: `VariantSwatchGroup`'s label truncation (`max-w-16`) was too narrow for real labels ("Large (16oz)", "Classic badge"), clipping them mid-word — found via direct screenshot inspection, not assumed.

The full findings list — including everything investigated but deliberately left unfixed, and why — is in the RC1 report's Regression/Risk/Technical-Debt sections.

## Phases 1-7 — What was fixed

**Correctness**: the caffeine-weight scoring bug (`recommendationEngine.ts`), with a new regression test asserting the specific per-branch weight so this can't silently reappear.

**Performance**: the `chapterProgress`/`VariantSwatchGroup` re-render bugs — both fixed by narrowing what each component actually subscribes to, not by adding memoization band-aids on top of an over-broad subscription. `VariantSwatchGroup` now reads its own category's store slice directly (a real, small, additive refactor of one customizer component, not a store or engine change) rather than receiving parent-computed props recreated on every hover anywhere in the panel. Coffee/Foam's material-cache bypass fixed to match every sibling part's existing pattern. The logo texture cache's missing disposer added. Two more `useMemo` gaps closed (`RecipeSummary`, `MiniCart`) to match their own sibling components' already-stated "memoize derived totals" requirement.

**Engine health**: wired real publishers for the 5 dead shared uniforms (`publishTheme`/`publishQualityTier`/`publishLightingIntensity` from `CupScene.tsx`'s already-computed values; `publishInteractionState` from `CupAssembly`'s existing interaction state machine) plus a 6th, `uPhysicsIntensity`, which had never had a publisher at all despite being labeled "Milestone 3" since Sprint 2.4. `dampVector3` relocated out of `engine/camera/` into `useSmoothedVector3.ts` itself (a 4-line duplicate, not a shared import) — closing a real, if harmless, violation of the frozen Performance Manager's "no outward dependencies" contract.

**Motion consistency**: three hardcoded, un-tokened transitions in the cart flow replaced with the project's own motion tokens (`OrderConfirmation`'s hand-rolled overshoat curve → `springs.bouncy`, the exact preset already built for this; `AddToCartButton`/`CartIcon` → `durations`/`easings`/`springs`). The AI Concierge's skeleton-to-result reveal — its single biggest payoff moment, previously a bare conditional swap — now uses the same `AnimatePresence` pattern every sibling feature's equivalent state change already established. The Drink Composer's ingredient add/remove/reorder — previously instant, contradicting the "no abrupt transitions" brief — now animates via `layout` + `AnimatePresence`, matching `DrinkCard.tsx`'s own precedent for the identical "list reflow" shape.

**Accessibility**: `CategoryFilter` harmonized onto the `radiogroup`/`radio`/`aria-checked` pattern `VariantSwatchGroup` already established (both are single-select groups; `aria-pressed` communicates independent toggles, which was misleading). `ChapterNav`'s chapter-jump dot rail — previously `hidden` below the `lg` breakpoint, undermining its own "keyboard navigation" claim — is now visible at every width, with a real 44px touch target per dot (matching this project's established minimum) rather than the 10px visible dot itself being the only hit area. A stale doc comment in `VariantSwatchGroup` (claiming `CategoryFilter` used `aria-pressed` "the same convention," when the code used `aria-checked`) corrected. `aria-pressed` added to a favorite-toggle button in `CartExperience` that was missing it relative to its sibling in `CartItemRow`. `focus-visible` styling added to a `PresetSaveControls` button that was missing the project's standard focus ring.

**Visual polish**: the truncation bug fixed (`max-w-16` → `max-w-24`, verified by screenshot showing full labels). Cart/Checkout/Confirmation's empty states — previously a small, sparse dashed box lost in a mostly-empty page — given real visual presence (larger icon, a two-line message, a subtle background tint), verified by screenshot. `syrup`'s hardcoded hex color replaced with a token-derived one (a lighter step of the same brand-accent ramp "caramel" already uses); the two genuine token-system gaps (ice's icy blue, the 5-color sprinkle palette) given explicit, reviewed "deliberate exception" comments instead of being silently non-compliant.

## What was investigated and deliberately left unfixed

Per the sprint's own explicit rule — "if any existing implementation appears wrong: STOP, document the issue, only redesign if it violates an existing frozen contract" — several real, genuine findings were **not** turned into code changes this sprint, because fixing them correctly needed either a scope decision only the user should make, or more dedicated visual-verification time than was available alongside everything else in this sprint:

- **The Hero/Customizer/Concierge camera framing clips the cup's lid at common viewport heights.** Confirmed via direct screenshot at 1440×900. Investigated the cause (`Hero.tsx`'s canvas is deliberately full-bleed behind a floating glass navbar — a real, stated design intent, not an oversight) before deciding this is a composition/preset-tuning question, not a bug — and the `hero` camera preset is the single most-reviewed, most-load-bearing visual asset in the entire project, unchanged and re-approved across every milestone review so far. Changing it without a dedicated visual QA pass (including re-baselining every visual-regression screenshot it affects) was judged too risky to do as one line item inside an already-enormous sprint. Documented, not fixed.
- **`--spacing-section`/`--spacing-section-sm` remain unused design tokens.** Real (confirmed via grep: zero consumers anywhere). Investigated wiring them into the 8 routes' hand-tuned top/bottom padding values the audits flagged — found the token values (128px/64px) don't exactly match any route's current, already-converged-upon spacing, meaning applying them would be a real, visible layout change across most of the app's routes, not a no-op rename. Deferred rather than risk an unverified, sitewide spacing shift this late.
- **The `IEventBus`/`IAssetManager` naming mismatches the engine audit found** (`emit`/`on` vs. the docs' `emit`/`subscribe`/`unsubscribe`; `resolveAsset`/`loadModel`/`preloadModel` vs. the docs' `resolve`/`load`/`preload`) are real, but renaming either would be a breaking API change across dozens of already-shipped call sites for a purely cosmetic documentation mismatch — the engine audit's own explicit recommendation was to document, not touch. Docs corrected in Phase 10 instead.
- **A live-region announcement for cart quantity changes** (flagged by the Storytelling/Cart audit) is a real, worthwhile a11y enhancement, but doing it correctly — without double-announcing alongside the existing `cart:item-added`/`-removed` announcer — needed a small design decision (a new, more specific event, or a component-local announcement) this sprint didn't have a safe, low-risk slot for. Deferred, not silently dropped.
- **The Architecture Freeze's own scenario-7 risk** (free cup drag-rotation and `/story`'s scroll-driven camera transitions can both want the camera at once) remains unresolved, exactly as flagged when `/story` shipped in Sprint 3.7. Real, but designing the actual interaction guard (which state wins, how the handoff feels) is a UX decision, not a mechanical fix — flagged again here rather than implemented under time pressure.
- **The GLB/KTX2 asset pipeline and `useGestureRecognizer`** remain fully built, tested, and completely unused in production, 6+ sprints after being built. Not a bug — a genuine roadmap question (is a real 3D asset or a 2D gesture-driven control still coming?) that belongs to whoever plans Milestone 4, not something Sprint 3.8 should decide unilaterally.

## Sign-off

Unit tests: **280/280 passing**, 41 files (1 new regression test this sprint). `tsc --noEmit`, `eslint`, and `next build` all clean throughout — checked after every batch of fixes, not just once at the end.

Full project-wide e2e regression (241 tests, 3 browsers): **237 passed, 4 failed, 8 skipped.** Every failure individually isolated and root-caused before being accepted, not assumed:
- `physics.spec.ts`'s Ice Cubes test (chromium) — passes cleanly alone; the same resource-contention-under-full-parallelism pattern documented since Sprint 3.4.
- `composer.spec.ts`'s reduced-motion test (webkit) — passes cleanly alone; same category as above, a different specific test hit by it this run (which test flakes under load varies run to run, already noted in prior sprints' reviews).
- `customizer.spec.ts`'s reduced-motion keyboard-commit test (webkit) — the exact, already-extensively-documented (since Sprint 3.3) WebKit+reduced-motion Playwright keyboard-automation quirk, confirmed genuinely intermittent via a 3x isolated repeat (2 failed, 1 passed) rather than deterministic. Given this sprint's `VariantSwatchGroup` rewrite touches the exact commit path this test exercises, the underlying mechanism was independently re-verified via 4 other passing tests in the same file (click-commit, keyboard-commit under normal motion, touch-commit, and a full sequential suite run where this same test passed) — all confirming the refactor's core commit logic is sound. The flake is real, pre-existing, and specific to the reduced-motion+WebKit+keyboard-automation intersection, not a new defect in the refactored component.
- `stabilization.spec.ts`'s hero-dark visual-regression baseline (webkit) — the same non-deterministic WebGL cup-mesh rendering noise documented since Sprint 3.3.

Zero new regressions from this sprint's own changes. Every fix in this sprint was verified individually (tsc/eslint/targeted test runs) before being folded into the full regression run, and the one test file needing an update alongside an app fix (`menu.spec.ts`, after the `CategoryFilter` accessibility change) was updated in the same commit as the fix, not left broken.

Waiting for approval before Milestone 4 (production deployment, real backend integration, launch preparation) begins, per explicit instruction.
