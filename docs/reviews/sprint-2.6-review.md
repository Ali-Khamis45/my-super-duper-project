# Sprint 2.6 — Engine Stabilization & Production Readiness: Review

Sprint 2.6 hardened the engine built across Sprints 2.1–2.5 into a production-ready platform: an integration audit that found and fixed a real activation bug, a new cross-browser/visual-regression test harness (Playwright, this sprint's tooling decision), a real Engine Health Dashboard, and a battery of stability/memory/GPU/accessibility checks run against a live browser, not just assumed from reading code. Per its own brief: no new rendering features, no new shaders, no new visual systems — stabilization only. This doc is also this sprint's Regression Report, Performance Report, Accessibility Report, and Engine Health Report — one document, not four thin ones, matching every prior sprint review's consolidation.

**Scale**: 3 new source files (`engine/devpanel/engineHealth.ts`, `EngineHealthPanel.tsx`, `engineHealth.test.ts`), 15 modified source/doc files, a new Playwright suite (`playwright.config.ts` + `e2e/stabilization.spec.ts` + `e2e/long-running.spec.ts`, 36 tests across 3 browser projects, 6 committed visual-regression baseline screenshots), 4 new unit tests (150 total project-wide, 26 files). `tsc`, `eslint`, `next build` all clean. 31 of 36 Playwright tests pass (5 skipped by design — 4 Chromium-only CDP tests × non-Chromium browsers, 1 documented WebKit platform limitation), fully green when run serially; occasional timing-sensitive flakiness observed only under heavy parallel load on this single dev machine, never a product-code failure (see Regression Report below).

## Architecture review

**One real integration bug found by tracing the actual call graph, not assumed from the file tree**: `engine/analytics/eventBridge.ts`'s EventBus subscriptions (`cup:rotated`, `quality:auto-changed`, `performance:degraded`, `memory:pressure`) only ever activated because `useCupInteractionState.ts` — a hero-cup-specific feature hook — imported the module for its side effect. Today this "works" only because the sole route (`/`) always mounts the hero cup; a future route without it would silently run with Analytics never wired up, and nothing in the code would signal that. Fixed by moving the side-effect import to `app/providers.tsx` (the actual app root, wrapping every route), and removing it from the feature hook. This is the sprint's clearest example of what "Engine Integration Audit" is for: co-existence isn't integration — a cross-cutting engine subsystem's activation must not depend on which feature happens to import it first.

**One-directionality re-verified by grepping the actual import graph, not re-asserted from memory**: every `@/engine/performance` import found across the codebase is either a type-only `QualityTier` import (compile-time only, no runtime coupling) or a legitimate one-directional read (`materials/themeBridge.ts`, `assets/textures.ts`, `devpanel/DevPanel.tsx` all read `performanceManager`/`resolveAssetQualityOptions`, never write to it). Zero imports run the other direction. The Engine Health Dashboard's aggregation deliberately lives in `engine/devpanel/`, not `engine/performance/` — `runtimeProfiler.ts`'s own doc comment (written in Sprint 2.5, before this sprint existed) had already drawn this exact boundary: combining material/texture/shader stats inside the Performance Manager would mean it importing from Materials/Assets/Shaders, a direct rule violation. The Debug Layer isn't bound by that rule — a pure sink nothing else depends on — so it's the correct owner of a cross-cutting read across every manager's already-public stats accessors (`getTextureCacheStats`, `getModelCacheStats`, `getMaterialCacheStats`, `shaderRegistry`, `getShaderDiagnostics`, `appEvents.getEmitCount`).

**Additive instrumentation, not a rewrite**: `createResourceManager` gained `size`/`hits`/`misses` (previously only `createSyncCache` tracked hit/miss — an inconsistency this sprint closed for symmetry), `createSyncCache` gained `size`, and `EventBus` gained `getEmitCount()`. All three are pure additions to already-frozen public contracts — existing call sites are untouched, verified by the fact that all 150 pre-existing-plus-new unit tests and the full production build stayed green through every step.

## Regression Report

**Full verification suite, clean**: `npx tsc --noEmit`, `npx eslint .`, `npx vitest run` (150/150), `npm run build` (same 6 static routes as every prior sprint) all pass after every change this sprint made, checked incrementally rather than once at the end.

**Cross-browser e2e (Playwright, new this sprint)**: 36 tests × 3 engines (Chromium, Firefox, WebKit). Fully serial (`--workers=1`) runs are 100% green: 31 passed, 5 correctly skipped. Two real, root-caused findings surfaced along the way, both fixed:

- The first stabilization-suite run timed out on nearly every test because the selector assumed `role="application"` lived on the `<canvas>` tag. Inspecting the live DOM directly showed React Three Fiber's `<Canvas>` actually places `role`/`aria-label`/`tabIndex`/the keyboard handler on its *wrapping* `<div>`, with the raw `<canvas>` carrying no attributes at all — confirmed by reading the rendered HTML, not assumed. This is standard, correct ARIA practice for canvas content (a bare `<canvas>` has no inherent semantics), not an app bug — the test's own selector was wrong. Fixed by targeting `[role="application"]` for interaction/a11y and the nested `canvas` only for pixel-content checks.
- The visual regression baseline's first capture attempt showed a 14% pixel diff between two "identical" captures. Diffing the images directly showed the delta was 100% confined to the cup's silhouette, zero diff on any static DOM content — the app's own idle ambient auto-rotation (`CupAssembly.tsx`, ~0.12 rad/s) makes the cup a moving target frame-to-frame. Fixed by capturing under `page.emulateMedia({ reducedMotion: "reduce" })`, which reuses the app's own already-tested reduced-motion path (`usePrefersReducedMotion` → `CupAssembly`'s idle-rotation gate) to freeze it — not a widened tolerance that would also hide a real regression, and not new test-only scene-freezing machinery.

**Known, accepted flakiness (environmental, not product)**: when all three browser projects and both spec files run in parallel on this single dev machine (which was also running the dev server, prior Chrome instances, and everything else this session spun up), 2–3 tests occasionally exceed their timeout or show a small visual diff — traced to real resource contention (confirmed: the same tests pass cleanly and deterministically every time when run serially or in isolation). This is the same category of finding Sprint 2.4's review already disclosed for headless-capture flakiness on reused Chrome profiles — documented rather than chased into a false sense of CI-grade determinism this sprint didn't set out to build.

**Hero renders correctly across the theme × quality-tier matrix**: visual regression baselines committed for light/dark theme in all 3 engines (6 images); the CPU-throttle stress test (below) additionally exercises all 5 quality tiers live.

## Performance Report

**No regression versus the Sprint 2.5 baseline**: re-running that sprint's exact CPU-throttle methodology (headless Chrome, CDP `Emulation.setCPUThrottlingRate(25)`) against this sprint's code reproduced the identical tier sequence — `ultra → high → medium → low → minimal`, one step at a time — with the same fast-downgrade/slow-upgrade hysteresis shape as before. Zero behavioral drift from this sprint's integration fixes or new instrumentation.

**A new, real long-running check**: `e2e/long-running.spec.ts`'s repeated-quality-switching test toggles CPU throttling on and off four times via CDP, sampling `performance.memory.usedJSHeapSize` between cycles. Heap growth stayed well under the 4× sanity bound across all runs — real per-tier allocation (shadow-map render targets resizing between 256²–2048² as the tier changes) is expected and visible in the Engine Health Dashboard's live `gpu tex` reading (observed swinging 27→107→27 during a throttle cycle, settling back down each time — consistent with resize, not a leak), but it doesn't compound.

**Scaled idle soak, not a literal 30 minutes**: a 20-second idle-with-sampling test ran clean (zero console/page errors, canvas alive throughout) three times across engines. A real unattended 30-minute soak wasn't run this session — this is a session-time-budget decision, not a capability gap, and is recommended as a scheduled/nightly job rather than something to fake here with an inflated claim.

**Two of the brief's named long-running scenarios have no real feature surface yet, and are documented as such rather than faked**: "repeated camera transitions" — only one camera preset (`hero`) exists; multi-preset transitions are explicitly deferred to Milestone 6 ([03_3D_ENGINE.md](../03_3D_ENGINE.md)'s Camera paths section). "Repeated asset disposal" — no real `.glb`/texture files exist anywhere in `public/` (true since Sprint 2.2, still true now), so the async resource caches this scenario would exercise have zero live production traffic; the one real cache under live churn (materials, via theme switching) is covered by the repeated-theme-switching test instead.

## Memory review

Covered above (Performance Report's heap-growth check) rather than split into a separate section — the two are the same investigation in this sprint (CPU-throttle-driven tier churn was the only realistic way to force repeated allocation/deallocation cycles worth measuring, given no long-session user-driven memory pressure scenario exists yet either).

## GPU review

**Resource disposal verified at the call-site level, not just via existing eviction unit tests**: `disposeTexture`/`disposeGLTF`/material eviction all call real `THREE.Object.dispose()` — confirmed by reading `engine/assets/textures.ts` (`texture.dispose()`), `engine/assets/glb.ts` (per-mesh `geometry.dispose()` + `material.dispose()` during GLTF traversal), and `engine/materials/cache.ts` (`onEvicted`/`invalidate`/`clear` all call `material.dispose()`). Sprint 2.3's LRU-eviction unit tests already proved the *cache* behavior; this sprint cross-checked that eviction actually reaches a real GPU-resource `.dispose()` call, not just a JS reference drop.

**Production Bundle Audit**: `.next/server/app/*.js` contains zero matches for `THREE.Scene`/`WebGLRenderer` — the SSR boundary from Sprint 1 still holds after 5 more sprints of engine growth. `npm audit --omit=dev` flags 3 high-severity CVEs, all transitive inside Next.js's own bundled `postcss`(8.4.31)/`sharp`(0.34.5), with `npm audit fix --force`'s only offered resolution being a downgrade to `next@9.3.3` — a catastrophic, wrong fix, not applied. Real-usage exposure is checked, not assumed: the flagged PostCSS CVEs require processing *attacker-controlled* CSS input, and this project's PostCSS pipeline only ever processes first-party, developer-authored CSS (Tailwind, `tokens.css`); `sharp` is Next's optional server-side image-optimization dependency, and `next/image` is never imported anywhere in this codebase (`grep` confirms zero matches), so the vulnerable code path has no reachable call site in this app at all. Tracked as a known, low-real-risk, upstream-owned transitive issue — revisit when Next.js ships a patched dependency, not by dependency surgery today.

## Accessibility review

**Keyboard**: skip link reachable and focus-visible via Tab in Chromium/Firefox — real, e2e-verified, not just structurally asserted. WebKit is a genuine, documented exception, not a bug: pressing Tab in Playwright's WebKit focuses the first `<button>`, skipping the skip link's real, correctly-marked-up `<a>` entirely — confirmed directly by inspecting `document.activeElement` after each Tab press. This is Safari's well-known default behavior (only form controls are in the Tab order by default; links require the user to enable "Full Keyboard Access") — every website's skip link has the same experience in default Safari, not a defect specific to this one. Documented and skipped in the suite with the reason inline, per this sprint's own "Safari (document any limitations)" allowance.

**Touch**: a real touch-emulated drag (`hasTouch: true`, `page.touchscreen.tap` + a mouse-move swipe simulating the same Pointer Events path) produces zero console errors across all 3 engines — confirms React Three Fiber's unified Pointer Events handling (no separate touch code path to diverge) still holds.

**Reduced motion**: verified via `page.emulateMedia({ reducedMotion: "reduce" })` — the interactive region stays focusable and keyboard-operable, zero errors. This is the same mechanism that now also deterministically freezes the visual regression baseline (see Regression Report).

**Focus / contrast**: the interactive cup region's `aria-label`/`tabindex` attributes verified present and correct via e2e assertion. Contrast was **not** re-audited this sprint — `git diff --stat HEAD -- src/design-system src/styles` shows zero changes to any color token or design-system file this sprint, so Milestone 1's already-passed CDR contrast audit still applies; re-running it would have been busywork against unchanged surface area, not real verification.

**Screen readers**: not tested with a real assistive-technology pass this sprint (no AT available in this environment) — the same honest, already-disclosed limitation as every prior sprint's accessibility section; ARIA role/label structure was verified programmatically (above), which is a proxy, not a substitute, for real AT testing.

## Creative Director Review

**Delivered, correctly scoped as polish, not a new visual system**: the WebGL context-loss fallback used to pop in/out instantly (a real behavior verified functionally in Sprint 2.1, now also e2e-tested this sprint) — jarring for a failure mode that's already disorienting on its own. It now fades via the existing `fadeIn` Framer Motion preset (`engine/motion/presets.ts`, established Milestone 1), wrapped in `AnimatePresence` — reusing the project's existing motion vocabulary rather than inventing a second one, and skipping the animation outright under reduced motion per the established "disable, don't downgrade" policy. This is exactly the brief's own example list ("Transition quality... micro-interactions") — a small, honest, verified improvement to an already-correct mechanism, not scope creep into new visual features, which this sprint's brief explicitly excluded.

## Production Readiness Review

**Green across every gate that exists**: type-checking, linting, unit tests, production build, and now a real multi-browser e2e suite all pass. The Engine Health Dashboard (`engine/devpanel/engineHealth.ts` + `EngineHealthPanel.tsx`) gives production debugging real, live visibility — frame time, draw calls, triangles, texture/material/model counts, compiled-vs-registered shader counts, cache hit ratio, current quality tier/mode, GPU texture count, and event throughput — all read through existing public accessors, dev-only (self-gated, mirroring `DevPanel`'s own convention), registered via the same `registerDevPanel` extension point Sprint 2.4 built and gave its first real consumer.

**What's still genuinely open, stated honestly rather than implied solved**: no real 30-minute unattended soak was run (scaled to 20s this session); no real Safari (macOS) or screen-reader pass exists; the visual-regression harness has known parallel-execution flakiness on a single dev machine that a real CI runner with dedicated resources would likely not exhibit; `npm audit`'s 3 high-severity findings are tracked-but-unfixed pending an upstream Next.js release. None of these block calling the engine production-ready for what this project actually is today (a single-route hero experience) — they're the concrete punch list for whoever runs this in a real CI environment next.

## Retrospective

### Technical debt

- The visual-regression baseline's parallel-execution flakiness (Regression Report) is worth a follow-up if/when this suite gets wired into CI: either dedicated CI runner resources (removing the single-dev-machine contention that causes it) or an explicit `workers: 1` pin for the visual-regression project specifically.
- `npm audit`'s 3 high-severity transitive CVEs (GPU review) have no available fix today short of a Next.js major-version downgrade this project won't take. Re-check on the next routine Next.js version bump.

### Architectural observations

- The `eventBridge.ts` activation bug is this sprint's clearest example of why an "integration audit" is a distinct activity from "does the code compile and pass its own tests" — every individual piece (the EventBus, the subscriptions, the hook that happened to import it) was correct and tested in isolation; the bug was purely in *how* they were wired together, findable only by tracing the actual runtime activation path end to end.
- `runtimeProfiler.ts`'s Sprint 2.5 doc comment predicting exactly where Engine Health aggregation would need to live (the Debug Layer, not Performance) turned out to be exactly right when this sprint actually needed to build it — a good sign that the one-directionality rule's boundary was drawn in the right place from the start, not something this sprint had to discover the hard way.
- Adding `size`/`hits`/`misses` symmetrically to both `createResourceManager` and `createSyncCache` (previously only the sync one tracked hit/miss) is a small but real consistency fix across this project's "one convention, multiple applications" factory family — worth remembering as a standing check whenever a new sibling of an existing factory pattern gets built: does it expose the same introspection surface as its siblings, not just the same core operations.

### Possible improvements

- The Engine Health Dashboard's `eventsPerSecond` reading is accurate but bursty (events fire in clusters around real state transitions, not evenly) — a smoothed/windowed rate would read more legibly on the live overlay, not attempted this sprint since the raw instantaneous rate was sufficient to prove the instrumentation works.
- A real manual/user-facing quality-tier picker (referenced but not built — `mode` has existed as `"automatic" | "manual"` since Sprint 2.5 with no UI ever writing `"manual"`) would make "repeated quality switching" testable as a real user scenario instead of only via CDP throttling — worth revisiting whenever a settings surface exists to host it.

## Sign-off

`git status` confirms every change this sprint is real, working, verified implementation — 4 new unit tests (150 total), a new 36-test Playwright suite (31 passing, 5 documented skips, 100% green serially), `tsc`/`eslint`/`build` all clean, one real integration bug found and fixed, zero behavioral regression against the Sprint 2.5 performance baseline. Waiting for approval before Milestone 3 begins.
