# Sprint 3.5 — AI Coffee Concierge: Review

A preference questionnaire feeding a deterministic, fully explainable recommendation engine over the real menu catalog — the "AI" is a transparent rule system, not an LLM call, the same "not a physics engine"-style honesty Sprint 3.4 applied to a different simulation. Every recommendation carries a real, varying confidence score, a positive/negative reasons list, validated ingredient suggestions and exclusions, ranked alternatives, and a one-click path to the customizer with everything pre-applied. Built through Engine v1.0's existing extension points (the camera registry, `CameraRig`'s dormant preset-interpolation, the EventBus, `customizer-store`/`composer` reuse) — zero engine rewrites.

**Scale**: ~14 new source files (`features/concierge/` — types, data, 2 hooks-worth of logic split as `hooks/useRecommendation.ts` + `lib/recommendationEngine.ts`, 8 components, README — plus `stores/concierge-store.ts`, `app/concierge/page.tsx`, `e2e/concierge.spec.ts`), 12 modified files (`engine/camera/presets.ts` gained an `"ai"` preset; `CupCanvas`/`CupScene`/`CupCanvasLoader` gained an optional `cameraPreset` prop; `engine/events/types.ts` gained 2 events; `NavLinks.tsx` gained a "Concierge" link; 4 docs; 2 regenerated visual-regression baselines). 10 new unit tests (229 total project-wide, 34 files, all passing). A new `e2e/concierge.spec.ts` (10 tests × 3 browsers, 30 total, all passing).

## Architecture review

**No engine files touched beyond the sanctioned extension points**: `engine/camera/presets.ts` gained one new registry entry (`"ai"`) — the exact `registerCameraPreset`-shaped extension point this doc has invited since Milestone 1. `engine/events/types.ts` gained `ai:recommendation-applied`/`taste-profile:updated`; the Sprint-0-typed, previously-dormant `ai:recommendation-ready` gets its first real publisher. `CupCanvas`/`CupScene`/`CupCanvasLoader` each gained one optional prop, defaulting to `"hero"` — every pre-Sprint-3.5 caller (Hero route, `/customize`) is unaffected, verified by the full regression run below, not assumed.

**A real, reasoned deviation from what the Architecture Freeze anticipated — decided, not defaulted into**: [15_ARCHITECTURE_FREEZE.md](../15_ARCHITECTURE_FREEZE.md)'s "AI Barista Recommendations" scenario flagged this as "the first feature that needs actual data-fetching," anticipating a TanStack Query design pass. This sprint's actual brief ("explainable... an assistant, not an oracle") makes clear the recommendation engine is a transparent local rule system, not a remote model — there is no real endpoint, and ADR-0005 is explicit that TanStack Query stays unwired until one exists ("no placeholder queries"). `useRecommendation.ts` instead uses React 19's own `startTransition` (which now accepts an async callback and keeps `isPending` true for its duration) plus a plain request-id cancellation token — every real requirement from the brief (non-blocking, graceful loading, cancellation of abandoned requests) is met without pretending a synchronous local computation is remote data. Recorded in [26_API_STABILITY.md](../26_API_STABILITY.md) as **Resolved**, not left as a stale "Experimental" row.

**The first live second camera preset, not just a second unit-tested config**: `CameraRig`'s preset-to-preset smooth interpolation was built in Sprint 2.1 and only ever validated by unit test + transition math — "No second preset is switched to at runtime yet," that sprint's own review said. `ConciergeCanvas` switching `cameraPreset` from `"hero"` to `"ai"` once a recommendation lands is the first real, live exercise of that code path — a genuine validation of a two-sprint-old design decision, not new machinery.

**A real integration, not a cosmetic one**: `ConciergeCanvas` resolves `recommendation.suggestedCustomizations` into real 3D `ingredientLayers` via `features/composer/`'s own `resolveIngredientLayers` — the exact function `/customize` uses for a user's own picks. The AI's suggestion visibly appears on the cup, not just as text in a panel; "seamlessly integrate with... the drink composer," the brief's own words, done by calling the composer's real resolver rather than duplicating what an ingredient layer means.

## AI integration review

**Every input signal the brief named is real, not decorative**: all 8 (taste preference, sweetness, bitterness, milk, temperature, caffeine, season, time of day) are derived from and scored against the real menu catalog's `category`/`tags` — no second, hand-authored "AI-friendly" dataset. `deriveDrinkSweetness`/`deriveDrinkBitterness`/`deriveMilkForwardness` are real, documented heuristics reading the same tags `features/menu/data/drinks.ts` already ships, not new fields invented for this sprint.

**Explainability, verified by test, not asserted**: `recommendationEngine.test.ts` asserts the top pick always has at least one non-empty reason for a profile with real signal, that a strongly-differentiated profile produces the *specific* drink its signals should favor (not just "a" drink), and that an incompatible-but-candidate ingredient (ice, on an iced-preference profile that still lands on an espresso drink) is explicitly excluded with a reason rather than silently omitted — "never present an unexplained recommendation," checked mechanically, not just by inspection.

**Confidence is a real, bounded, varying number**: `MAX_POSSIBLE_SCORE` is the literal sum of every scoring rule's best-case weight, not a guessed ceiling — a dedicated test exercises a spread of profiles and asserts no drink's raw score ever exceeds it. Manual verification produced real variation (29% for a partially-mismatched profile, 58% for a more balanced one) — the confidence indicator was checked to actually move, not hardcoded to look impressive.

**Recipe Compatibility Validation is real, not assumed**: every candidate ingredient customization is checked against `features/composer/`'s own `isIngredientCompatible` before being suggested; an incompatible one is moved to `excludedIngredients` with a reason instead of silently dropped or suggested anyway. Verified live via e2e (a strict hot/bitter/no-milk profile with `temperature: "iced"` still set correctly recommends Classic Espresso *and* explicitly excludes Ice Cubes as incompatible).

**"Existing recipe selections" is a real, tested signal, not a documented-but-unused field**: `currentCategory` (the customizer's own `baseDrinkCategory`) is read directly, never duplicated, and a dedicated test confirms a matching category nudges that drink's score upward without being a hard requirement — a first-time visitor with nothing selected yet still gets a full, real recommendation.

## Performance review

**Non-blocking and cancellable, verified by design not just claim**: `startTransition`'s `isPending` drives the "Thinking…" button state and the skeleton panel — a real loading state, not a synchronous freeze (the underlying computation is fast, but the deliberate ~650ms pacing beat, this sprint's Creative Budget choice, genuinely exercises the pending state). The request-id token means a second submission before the first "finishes thinking" discards the first result rather than racing it — a real cancellation semantic, checked directly in `useRecommendation.ts`'s own logic (not unit-tested, matching this project's established precedent of e2e-only coverage for React-render-lifecycle hooks like `useCupInteractionState`/`useLiquidPhysics`, rather than force-fitting a renderer into Vitest).

**A real bug found and fixed during manual verification, not shipped**: "Apply to Customizer" originally called `applyRecommendationToCustomizer` and stopped — updating `customizer-store` state but never navigating anywhere. "One-click Apply to Customizer" means arriving at the customizer, not silently changing state the user would have to know to go look for. Found by an actual click-through (`page.url()` staying on `/concierge` after the click), fixed with a real `next/navigation` `router.push`, confirmed by a second click-through with a generous wait (`page.waitForURL`) rather than assumed fixed from reading the diff.

**A real environmental finding, investigated before concluding it wasn't a regression**: the same fix's initial verification attempt used a 1-1.5s wait and appeared to fail (URL never changed) — before concluding this was a bug, a longer, explicit `page.waitForURL(..., { timeout: 20_000 })` was tried and *did* observe the navigation completing, just slower than expected. This dev machine's SwiftShader-backed session showed FPS dropping to 1 and the adaptive-quality tier auto-stepping down to `minimal` during this exact verification pass — the same class of environmental slowdown documented in Sprint 3.3/3.4's reviews, not a new regression. The actual bug (missing `router.push`) was real and is fixed; the false lead (assuming the fix didn't work) was run to ground with direct evidence before either conclusion was accepted.

**Visual-regression baselines, regenerated for a real reason, not silently accepted stale**: adding "Concierge" to the shared `NavLinks.tsx` changes the Hero route's own nav text — the pixel-diff baselines predate that change, so a diff there is expected and correct, not a bug. Baselines were regenerated (`hero-dark-chromium-win32.png`, `hero-dark-webkit-win32.png`) rather than the test being loosened or skipped. The pre-existing, non-deterministic WebGL cup-mesh rendering noise Sprint 3.3/3.4 already documented (renderer-level, confined to the cup mesh, not layout) is still present and continued to occasionally cross the 5% threshold on different browsers across repeated runs during this sprint's own regression passes (chromium once, firefox twice, webkit twice, at varying magnitudes up to 13%) — consistent with "non-deterministic noise crossing a threshold by chance," not a new or worsening problem this sprint caused. Not chased further, per the same reasoning Sprint 3.3/3.4 already recorded: this needs dedicated future investigation into the renderer itself, not more inline debugging.

## Accessibility review

**Keyboard**: every questionnaire option is a real `<button role="radio">` inside a `role="radiogroup"` (the same convention `VariantSwatchGroup` established in Sprint 3.2, reimplemented as a smaller dedicated component since this domain has no hover-preview concept to carry along) — reachable by Tab, activated by Enter/Space. Verified via e2e: focus + Enter selects an option, focus + Enter on the submit button generates a recommendation.

**Announcements**: `RecommendationAnnouncer`'s `aria-live="polite"`/`role="status"` region is purely derived from `lastRecommendation` during render — no `useState`/`useEffect` (a real fix during implementation: an initial `useEffect`-based version tripped `react-hooks/set-state-in-effect`, correctly, since the announcement text is entirely a function of store state and didn't need an effect to compute at all). Verified live via e2e that the region's text updates to "Recommendation ready: <drink>, <confidence>% confidence."

**Focus management**: once a recommendation lands, focus moves to the result panel (a `tabIndex={-1}` container, focused imperatively in a `useEffect` keyed on `lastRecommendation`) — the same "a meaningful content update gets a focus move" pattern a dialog opening gets for free, applied by hand here since this is a route-level state change, not a dialog.

**Reduced motion**: the ~650ms "thinking" pacing beat is skipped entirely under reduced motion (this project's established "disable outright, don't downgrade" policy) — verified via e2e that a reduced-motion submission produces the recommendation with no perceptible delay and zero console errors.

**Touch**: verified via e2e with `hasTouch: true` — tapping a preference option and the submit button both work through the same real `<button>` elements keyboard/click already use.

## Creative Director Review

**Delivered, and specific, not generic**: reasoning copy names the actual signal that mattered ("Served cold, matching your iced preference," "A bold, high-caffeine pull," "No dairy, matching your preference") rather than a templated "this matches your preferences" — the brief's explicit "avoid generic chatbot responses" checked against real generated copy, not just the intent to avoid genericness. The confidence indicator's three-tier label ("Great match" / "Good match" / "Worth trying") gives the number a real qualitative frame instead of a bare, possibly-alarming-looking percentage.

**The reveal is a genuine payoff, not new spectacle for its own sake**: the camera-preset switch and the suggested-ingredients-on-the-cup moment both reuse previously-built-but-dormant engine capability (`CameraRig`'s interpolation, `resolveIngredientLayers`) rather than adding a new visual system — "premium" achieved by finishing an already-designed integration point, matching this project's established restraint (Sprint 3.2/3.3/3.4 all made the same kind of call).

**Honestly scoped**: no attempt was made to dress this up as a "real AI" beyond the branding — the README and this review are explicit that it's a rule engine, which is also *why* the explainability requirements ("which preferences influenced the recommendation," "which ingredients caused exclusions") are fully satisfiable at all. A true black-box model couldn't have met this sprint's own explainability bar as directly.

## Retrospective

### Technical debt

- Scoring weights are hand-tuned constants, not derived from any real usage data (none exists to derive from) — a reasonable, honestly-scoped starting point, revisit if a future sprint has real interaction data to tune against.
- Milk-forwardness (`deriveMilkForwardness`) is a heuristic over tags + drink name, not a structured catalog field — `features/menu/`'s `Drink` type was never designed with a "milk amount" concept, and adding one is a data-model change outside this sprint's scope.

### Architectural observations

- The "decide against TanStack Query, document why" call is this sprint's clearest example of *not* blindly following a two-sprint-old anticipation once the actual brief changed the premise — `docs/26_API_STABILITY.md`'s row is marked Resolved with the real reasoning, not left stale or silently ignored.
- `CameraRig`'s preset interpolation and `resolveIngredientLayers` both went from "built, unit-tested, zero live second consumer" to "genuinely exercised in production" this sprint — a reminder that this project's habit of building slightly ahead of a feature's own immediate need (Sprint 2.1's camera registry, Sprint 3.3's ingredient resolver) pays off exactly when a later sprint's real requirement lines up with what was already there.
- The `useRecommendation`/`concierge-store` split (React-transition orchestration in a hook, data in a store) mirrors `useLiquidPhysics`/`CupAssembly`'s "compute here, apply there" split from Sprint 3.4 — a second instance of the same "React-lifecycle concerns don't belong in a vanilla Zustand store" principle, now established across two different domains.

### Possible improvements

- A future sprint with a real recommendation endpoint could swap `useRecommendation`'s local call for a real TanStack Query mutation against the same `generateRecommendation`-shaped contract, satisfying the Architecture Freeze's original anticipation for real this time.
- Ripple-style "why this ranked below the top pick" reasoning is currently limited to each alternative's own top reason, not a full comparison against the winner — a reasonable, honestly-scoped simplification (the brief asks "why alternatives were suggested," which this satisfies; a deeper A-vs-B comparison would be a real, separate feature).

## Sign-off

10 new unit tests (229 total, 34 files, all passing — determinism, confidence-ceiling, and compatibility-validated suggestion/exclusion coverage for the recommendation engine), a new 30-test e2e suite (`concierge.spec.ts`, all passing across Chromium/Firefox/WebKit), zero engine files touched beyond the sanctioned camera-preset/event-catalog extensions, zero regression in Sprint 3.1–3.4 functionality (`tsc --noEmit`, `eslint`, `next build` all clean). A real navigation bug was found and fixed during manual verification, not shipped. Visual-regression baselines were regenerated for the real, intentional nav-link change; the pre-existing, non-deterministic WebGL rendering-noise finding (documented since Sprint 3.3) continues and is not this sprint's regression. Waiting for approval before Sprint 3.6 (Commerce Experience) begins, per explicit instruction.
