## Architecture review

**DDD's aggregate boundary held exactly as frozen**: one `Payment` aggregate root per `Order`, with `PaymentAttempt` as an owned entity (never its own repository, never referenced by id from outside `Payment`) — a declined card retries against the *same* `Payment`, producing a second `PaymentAttempt`, never a second `Payment`. This is the real reason `PaymentStatus` returns to `Pending` (not `Failed`) after a decline: the aggregate itself, not `Order`, tracks retry history.

**`IOrderPaymentCoordinator` follows the exact same same-transaction, direct-call pattern `IInventoryReservationCoordinator` established in Sprint 5.4** — `ConfirmPaymentCommandHandler`/`ProcessPaymentWebhookCommandHandler`/`CapturePaymentCommandHandler` call it directly, never through the outbox dispatcher, for the identical reason: "is this order actually paid" can't wait for an eventually-consistent consumer. [32_COMMERCE_EVENT_CATALOG.md](../32_COMMERCE_EVENT_CATALOG.md) has been updated with the full, real Payments event set and this reasoning, replacing the three sketch rows (`PaymentCaptured`/`PaymentFailed`/`PaymentRefunded`) the Phase 0 catalog carried.

**A real architectural gap found and fixed mid-sprint**: `CapturePaymentCommand` (a Phase 2-required CQRS command) was implemented correctly in its first cut but was completely unreachable — neither gateway ever produced an `Authorized`-only attempt for it to act on, since both defaulted to automatic capture. This is functionally a placeholder despite compiling and passing its own guard-clause tests, which this sprint's own Engineering Rules explicitly forbid. Fixed with a real, minimal `PaymentsOptions.CaptureMode` (`"Automatic"`/`"Manual"`) config, threaded through both gateways (including fixing a related Stripe status-mapping gap — `StripePaymentGateway.ToOutcome` had no `"requires_capture"` branch at all, which would have mischaracterized a genuinely-approved authorization as a failed payment) and both confirmation paths (`ConfirmPaymentCommand`/`ProcessPaymentWebhookCommand`), with idempotency guards against double-authorize. See [34_PAYMENTS_NOTIFICATIONS_SEARCH.md](../34_PAYMENTS_NOTIFICATIONS_SEARCH.md)'s own Sprint 5.5 status note.

**Both money-facing gaps this close-out was asked to resolve are now closed, not deferred:**

- **`CancelOrderCommand` now blocks cancelling a captured payment, rather than silently allowing it.** `CancelOrderCommandHandler` checks `IPaymentRepository.GetByOrderIdAsync` before mutating `Order`, and throws a new `PaymentCapturedException` (409, `payment-captured`) when the order's `Payment` is `Succeeded`/`PartiallyRefunded` — the same shape `PayOrderCommandHandler`'s own `PaymentInProgressException` already established for the symmetric in-flight case. The decision made explicitly: a **hard guard**, not an automatic refund-on-cancel pipeline — the safer of the two options this close-out's brief offered, since an automatic refund has its own real edge cases (partial refunds already applied, a payment that's since moved to a different terminal state) that deserve their own dedicated design pass rather than being rushed into this close-out. Staff/customers who need to cancel a paid order now get a clear, correct 409 telling them to process a refund first — never a silent, uncompensated cancellation. Regression test: `Handle_OrderHasACapturedPayment_ThrowsPaymentCapturedExceptionRatherThanStrandingTheCharge` (`OrderCommandHandlerTests.cs`).
- **`Payment.TimeoutAttempt` now has a real caller** — a lazy, on-next-access check, the same shape `InventoryReservationCoordinator`'s own lazy expiry-reclaim established in Sprint 5.4, not a new architectural pattern. `CreateCheckoutSessionCommandHandler` (the natural "next real access" point — a customer revisiting checkout, or explicitly retrying) checks whether the current `Processing` attempt has sat past a new, configurable `PaymentRetryOptions.StuckAttemptTimeoutMinutes` (15-minute conservative default); if so, it calls `Payment.TimeoutAttempt` and falls through to starting a genuinely new attempt, rather than the customer being stuck behind an attempt they already gave up on. Still under the threshold, the existing idempotent-no-op double-click behavior is unchanged. Regression test: `CreateCheckoutSession_ExistingProcessingPaymentPastTheStuckThreshold_TimesItOutAndStartsAFreshAttempt` (`PaymentCommandHandlerTests.cs`).

## Security review

Full detail in [36_SECURITY_MODEL.md](../36_SECURITY_MODEL.md)'s own "Payments security" section — summarized here:

- **No card data stored**, confirmed by construction (`PaymentMethod`'s shape can't hold a PAN/CVV even if a caller tried).
- **Real webhook signature verification** — Stripe's own SDK for `StripePaymentGateway`; a hand-implemented, byte-for-byte equivalent HMAC scheme for `FakePaymentGateway`, so the webhook endpoint's code path is identical regardless of active gateway. Timing-safe comparison (`CryptographicOperations.FixedTimeEquals`), not `==`.
- **Real replay protection** — `IIdempotencyStore.TryReserveAsync`, keyed by the gateway's own event id, a deliberate documented exception to the one-`SaveChangesAsync`-per-request rule so the reservation is atomic even under genuine concurrent delivery. Verified live via a real signed webhook delivery through the dev-only simulator, hitting the actual verify-correlate-capture pipeline (`PaymentEndpointsTests.cs`, Integration layer).
- **A real double-charge risk, found via live/E2E reasoning and fixed**: `PayOrderCommand` (staff manually recording an out-of-band payment) had no awareness of an in-flight gateway `Payment` — a customer completing a card checkout while staff simultaneously recorded the same order paid by cash could result in a real double charge, surfacing to the customer only as a confusing 409 with no automatic remediation. Fixed with a real guard (`PaymentInProgressException`, 409) — see [37_API_STABILITY_POLICY.md](../37_API_STABILITY_POLICY.md)'s own compliance record for the honest "is this breaking" analysis. Verified live end-to-end against real HTTP + real Postgres (`PayOrder_WhileARealPaymentIsInFlight_Returns409AndNeverRisksADoubleCharge`, Integration layer).
- **A real, symmetric money-safety gap, found and closed this close-out**: `CancelOrderCommand` had the mirror-image hole — no awareness of an already-*captured* payment, meaning cancelling a paid order could silently strand a real charge with no refund ever triggered. Closed with `PaymentCapturedException` (409) — see Architecture review above.
- **A real request-cancellation data-loss bug, found live and fixed**: `UnitOfWorkBehavior`'s "save on exception" recovery path (added Sprint 5.1 for refresh-token-reuse-detection) reused the request's own, possibly-already-cancelled `CancellationToken` for its own recovery save. A client disconnecting mid-`ConfirmPaymentCommand`, after a real capture had already mutated `Payment`/`Order` in memory but before the transaction committed, made the recovery save itself throw immediately — silently discarding an already-succeeded payment capture. Fixed with `CancellationToken.None` for the recovery save; this also retroactively hardens the original Sprint 5.1 scenario. Six new regression tests lock this in (`UnitOfWorkBehaviorTests.cs`).

## Performance review

**A real, live-verified performance/correctness bug, found via Playwright under concurrent load, not manual testing**: `ConfirmPaymentCommand`/`ProcessPaymentWebhookCommand` originally awaited the order-confirmation email's full SMTP round trip inline, inside the customer-facing HTTP response. Under a single manual curl this looked survivable (a slow ~6s response); under real concurrent browser load (4 parallel Playwright workers, each placing a real order) it produced a client-observed 499 (browser aborted the request before receiving a response) after ~17.6 seconds — even though the payment had already captured successfully server-side, `Payment.Status == Succeeded`, and the response the customer never saw would have said so. Fixed by making the email send fire-and-forget with `CancellationToken.None`, in both `ConfirmPaymentCommand` and `ProcessPaymentWebhookCommand` (which, investigated as part of the same fix, turned out to never send the confirmation email at all if the webhook — not the customer's own optimistic confirm call — was what actually resolved the payment; a real gap given that command's own doc comment specifically claims "the browser closed right after confirming is recoverable" via the webhook path). `SmtpEmailSender.SendAsync` already catches and logs every internal failure, so the fire-and-forget task can never fault unobserved. See [34_PAYMENTS_NOTIFICATIONS_SEARCH.md](../34_PAYMENTS_NOTIFICATIONS_SEARCH.md)'s own status note. Confirmed fixed post-infrastructure-repair too: a real `POST /auth/register` against the corrected stack now responds in well under a second, down from the multi-minute hangs observed before the SMTP root cause (below) was found.

No N+1 patterns found in the new query handlers — `GetPaymentQuery`/`AdminPaymentSearchQuery` resolve `OrderNumber` via the same batched cross-context repository-lookup pattern `InventoryReservationDto.OrderNumber` established in Sprint 5.4, never one query per row.

### The real infrastructure root cause, found and fixed (not just re-diagnosed)

The review draft going into this close-out attributed the 8 originally-failing tests (all of `orders.spec.ts`/`admin-orders.spec.ts`) to "a Mailhog SMTP handshake issue," disclosed but unresolved. This close-out found the actual root cause and fixed it at the infrastructure layer:

- **Root cause**: a stuck Windows-level TCP listener on port 1026 (`services.exe`, an HNS port-proxy artifact) was silently competing with Docker's own real port-forwarder (`com.docker.backend.exe`) for the same host port — confirmed via `Get-NetTCPConnection`/`Get-Process`, and confirmed to be host-side specifically (SMTP worked perfectly *inside* the Docker network, container-to-container, the entire time — Mailhog itself was never broken). It survived a Mailhog container restart, a full `docker compose down`/`up` stack recreation, a full Docker Desktop restart, and `wsl --shutdown` — none of which are guaranteed to clear a stale Windows-level port binding.
- **Fix**: remapped Mailhog's host SMTP port from 1026 to 1029 in `docker-compose.yml` (a genuinely free port, verified via `Get-NetTCPConnection` before use) and updated `appsettings.Development.json` to match. This is an infrastructure-layer fix for a host-port conflict, not an application-code workaround — no backend/frontend code changed to "route around" the problem.
- **Confirmed resolved, not just re-diagnosed**: a real SMTP send (Python `smtplib`, independent of any application code) landed in Mailhog's real inbox; a real `POST /auth/register` through the actual running application responded in under a second and its verification email was confirmed delivered.

**Real bugs found in the e2e suite itself, diagnosed and fixed (not dismissed as flakes):**

1. **`orders.spec.ts` registered a fresh account per test (6 registrations)**, tripping `AuthPolicy`'s real rate limiter once combined with `admin-orders.spec.ts`'s own registrations in the same run — a genuine 429, confirmed via API log timestamps, not a guess. Fixed by refactoring to `test.describe.serial` + one shared account (the same pattern `admin-inventory.spec.ts` already established in Sprint 5.4), cutting registrations from 6 to 3 while preserving exactly which tests still need a genuinely fresh/second identity (the "no orders yet" test, and the second customer in the ownership-isolation test).
2. **`admin-orders.spec.ts`'s "filters by status" test had a real race**: `count()` then a `for` loop re-querying `nth(index)` per iteration — Playwright auto-retries each `nth()` against the live DOM, so a filtered-list refetch settling *between* the count and a later index's own retry could fail on a list the app had actually rendered correctly (confirmed: the DOM snapshot at the one observed failure showed 8/8 rows correctly "Completed," matching "8 total" — the app was right, the test's own count-then-iterate pattern wasn't atomic). Fixed with a single `allTextContents()` snapshot instead.
3. **`payments.spec.ts`'s own "Receipt" locator used the wrong ARIA role** — `PaymentHistoryList.tsx` renders it as `<Button render={<Link/>}>`, a real anchor tag (role `"link"`), but the test queried `getByRole("button", ...)`, which never matched, producing a 90-second timeout with the correct link sitting right there in the DOM the whole time. Fixed by querying `getByRole("link", ...)`.

**A pre-existing, general WebKit finding, isolated and correctly scoped out of this sprint**: registration (`POST /auth/register` via the actual form) is unreliable on this machine's Playwright-bundled WebKit build — reproduced via `auth.spec.ts`'s own client-side password-validation test, which fails *before the request ever reaches the backend* (confirmed: zero register calls appear in the API log for the failing run). `auth.spec.ts` predates this sprint by four milestones and was never touched. This blocks WebKit coverage for every registration-dependent spec (`orders.spec.ts`, `admin-orders.spec.ts`, one test in `payments.spec.ts`) uniformly, which is itself the evidence this is a general, pre-existing WebKit/Windows form-interaction characteristic, not a Payments regression. Guest-only flows (`cart.spec.ts`, 3 of 4 `payments.spec.ts` tests) pass cleanly on WebKit. Flagged as a known limitation for a future dedicated investigation, not fixed here — it long predates and is orthogonal to this sprint's own scope.

**Three pre-existing, unrelated failures found and correctly scoped out**: `physics.spec.ts`'s console-error check trips on the browser's own routine "Failed to load resource: 401" log line for an anonymous visitor's silent `/auth/refresh` check (Sprint 5.1 code, already named as this exact class of finding in that sprint's own review); `story.spec.ts`'s "Crafting chapter" screenshot-diff assertion reproduces consistently in isolation (Sprint 3.7 storytelling code, last touched three milestones ago, `git diff HEAD` confirms zero changes this session). ## Retrospective

What went well: the `IOrderPaymentCoordinator`/`IInventoryReservationCoordinator` same-transaction pattern generalized cleanly a second time, with zero new architectural negotiation needed. The `CaptureMode` fix is a genuine example of this project's "no placeholder implementations" rule catching something a passing test suite alone would have missed forever, since `CapturePaymentCommand`'s own unit tests were all correct in isolation — the gap was in what called it, not what it did. This close-out's own insistence on root-causing rather than re-disclosing the Mailhog issue is the same discipline paid off a level deeper: what looked like an unfixable environmental blocker was a fixable, narrowly-scoped host port conflict once actually investigated with the right tools (`Get-NetTCPConnection`, container-vs-host isolation testing) instead of accepted as unresolvable.

What to carry forward: the "a side effect that must survive regardless of client disconnect needs `CancellationToken.None`, not the request's own token" lesson is now a real, twice-independently-discovered pattern in this codebase — worth a dedicated note in [41_BACKEND_DEVELOPMENT_STANDARDS.md](../41_BACKEND_DEVELOPMENT_STANDARDS.md). The lazy-reclaim-on-next-access pattern (`InventoryReservation.Expire`, now `Payment.TimeoutAttempt`) has proven itself twice — worth naming as a first-class pattern in that same standards doc for the next aggregate that needs "reclaim stale state without a background worker." `AuthPolicy`'s real rate limiter interacting with registration-heavy e2e suites is now a three-times-documented (Sprint 5.2, 5.4, 5.5) recurring friction — worth a real, permanent fix (a test-environment-only higher limit, or a shared-fixture-account convention applied project-wide) rather than a fourth sprint rediscovering it independently.

What's explicitly deferred, not forgotten: live verification of `StripePaymentGateway` against Stripe's real servers; the WebKit registration-form and `physics.spec.ts`/`story.spec.ts` findings (all pre-existing, all orthogonal to Payments — see Known limitations).
