# Sprint 5.5 — Payments Platform: Review

The Payments bounded context, real end to end: a `Payment` aggregate with child `PaymentAttempt` entities ([30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md)), full CQRS command/query set, two real `IPaymentGateway` implementations (`StripePaymentGateway`, `FakePaymentGateway`), real webhook signature verification and replay protection, EF Core migrations against a real PostgreSQL database, real frontend integration replacing the direct-to-confirmation checkout jump with a genuine charge step — plus a new `/admin/payments` area, the third real area the `Staff`/`Admin` roles reach. Verified against a real PostgreSQL database, the real backend running live, and a real browser (Playwright) — not mocks. **Ten real findings** were made via this verification (six fixed, four disclosed as known limitations rather than silently left standing), detailed below.

**Scale**: Backend — 1 aggregate (`Payment`) + 1 owned entity (`PaymentAttempt`), 4 value objects (`IdempotencyKey`, `PaymentProviderReference`, `PaymentMethod`, `PaymentFailure`), 8 domain exceptions, 10 domain events, 1 coordination service (`IOrderPaymentCoordinator`, the same direct-same-transaction pattern `IInventoryReservationCoordinator` established in Sprint 5.4), 10 CQRS commands/queries, 2 real gateway implementations + 1 idempotency store, 1 EF Core configuration + 1 migration (`AddPayments`) + 1 repository, 1 endpoint-group file (9 customer/admin routes + 1 dev-only webhook simulator), 28 new Domain tests + 31 new Application tests (25 command-handler tests + 6 `UnitOfWorkBehavior` regression tests) — **176 Domain + 80 Application tests passing, zero regressions**. Frontend — 1 API client file (`lib/payment-client.ts`), 1 new component (`PaymentProcessing.tsx`, the real charge step) plus real edits to `CheckoutExperience.tsx`/`OrderConfirmation.tsx`/`cart-store.ts`, 1 new feature directory (`features/payments/` — 2 hooks, 2 components) and 1 new admin feature directory (`features/admin/payments/` — 3 hooks, 3 components), 5 new routes (`/checkout/payment`, `/payments`, `/payments/[id]`, `/admin/payments`, `/admin/payments/[id]`), 1 new guard hook (`useRequireViewPayments`), 6 new `AppEvent` union members (`payment:started`/`-retried`/`-succeeded`/`-declined`/`-cancelled`/`-refunded`), 1 new e2e spec (`payments.spec.ts` — 4 tests) plus real updates to `cart.spec.ts`/`orders.spec.ts`/`admin-orders.spec.ts` for the new checkout flow. `tsc`/`eslint`/`dotnet build`/`next build` clean throughout (34 routes generated, all new Payments routes present).

## Architecture review

**DDD's aggregate boundary held exactly as frozen**: one `Payment` aggregate root per `Order`, with `PaymentAttempt` as an owned entity (never its own repository, never referenced by id from outside `Payment`) — a declined card retries against the *same* `Payment`, producing a second `PaymentAttempt`, never a second `Payment`. This is the real reason `PaymentStatus` returns to `Pending` (not `Failed`) after a decline: the aggregate itself, not `Order`, tracks retry history.

**`IOrderPaymentCoordinator` follows the exact same same-transaction, direct-call pattern `IInventoryReservationCoordinator` established in Sprint 5.4** — `ConfirmPaymentCommandHandler`/`ProcessPaymentWebhookCommandHandler`/`CapturePaymentCommandHandler` call it directly, never through the outbox dispatcher, for the identical reason: "is this order actually paid" can't wait for an eventually-consistent consumer. [32_COMMERCE_EVENT_CATALOG.md](../32_COMMERCE_EVENT_CATALOG.md) has been updated with the full, real Payments event set and this reasoning, replacing the three sketch rows (`PaymentCaptured`/`PaymentFailed`/`PaymentRefunded`) the Phase 0 catalog carried.

**A real architectural gap found and fixed mid-sprint**: `CapturePaymentCommand` (a Phase 2-required CQRS command) was implemented correctly in its first cut but was completely unreachable — neither gateway ever produced an `Authorized`-only attempt for it to act on, since both defaulted to automatic capture. This is functionally a placeholder despite compiling and passing its own guard-clause tests, which this sprint's own Engineering Rules explicitly forbid. Fixed with a real, minimal `PaymentsOptions.CaptureMode` (`"Automatic"`/`"Manual"`) config, threaded through both gateways (including fixing a related Stripe status-mapping gap — `StripePaymentGateway.ToOutcome` had no `"requires_capture"` branch at all, which would have mischaracterized a genuinely-approved authorization as a failed payment) and both confirmation paths (`ConfirmPaymentCommand`/`ProcessPaymentWebhookCommand`), with idempotency guards against double-authorize. See [34_PAYMENTS_NOTIFICATIONS_SEARCH.md](../34_PAYMENTS_NOTIFICATIONS_SEARCH.md)'s own Sprint 5.5 status note.

**Two real gaps found, disclosed, not fixed this sprint** — both are honest limitations of the shipped design, not silently swept under a passing test suite:
- `Payment.TimeoutAttempt` is real, domain-tested code with no real caller — no background sweep or lazy on-read check (the pattern `InventoryReservation.Expire`'s own lazy sweep established in Sprint 5.4) invokes it. A payment stuck mid-confirmation (client network drops before either `ConfirmPaymentCommand` or the webhook ever resolves it) has no automatic path out of `Processing`; the real, working recovery today is an explicit `CancelPaymentCommand` call.
- `CancelOrderCommand` (Sprint 5.3, unmodified) allows cancelling a `Paid` order with zero awareness of Payments — cancelling an order whose card was genuinely charged does not trigger a refund. This predates Sprint 5.5 (before real Payments existed, "paid" only ever meant staff-recorded cash), but a real card charge makes the gap materially more consequential. An automatic refund-on-cancel pipeline is real, non-trivial new scope with its own edge cases this sprint's brief never named.

## Security review

Full detail in [36_SECURITY_MODEL.md](../36_SECURITY_MODEL.md)'s own new "Payments security" section — summarized here:

- **No card data stored**, confirmed by construction (`PaymentMethod`'s shape can't hold a PAN/CVV even if a caller tried).
- **Real webhook signature verification** — Stripe's own SDK for `StripePaymentGateway`; a hand-implemented, byte-for-byte equivalent HMAC scheme for `FakePaymentGateway`, so the webhook endpoint's code path is identical regardless of active gateway. Timing-safe comparison (`CryptographicOperations.FixedTimeEquals`), not `==`.
- **Real replay protection** — `IIdempotencyStore.TryReserveAsync`, keyed by the gateway's own event id, a deliberate documented exception to the one-`SaveChangesAsync`-per-request rule so the reservation is atomic even under genuine concurrent delivery.
- **A real double-charge risk, found via live/E2E reasoning and fixed**: `PayOrderCommand` (staff manually recording an out-of-band payment) had no awareness of an in-flight gateway `Payment` — a customer completing a card checkout while staff simultaneously recorded the same order paid by cash could result in a real double charge, surfacing to the customer only as a confusing 409 with no automatic remediation. Fixed with a real guard (`PaymentInProgressException`, 409) — see [37_API_STABILITY_POLICY.md](../37_API_STABILITY_POLICY.md)'s own compliance record for the honest "is this breaking" analysis.
- **A real request-cancellation data-loss bug, found live and fixed**: `UnitOfWorkBehavior`'s "save on exception" recovery path (added Sprint 5.1 for refresh-token-reuse-detection) reused the request's own, possibly-already-cancelled `CancellationToken` for its own recovery save. A client disconnecting mid-`ConfirmPaymentCommand`, after a real capture had already mutated `Payment`/`Order` in memory but before the transaction committed, made the recovery save itself throw immediately — silently discarding an already-succeeded payment capture. Fixed with `CancellationToken.None` for the recovery save; this also retroactively hardens the original Sprint 5.1 scenario. Six new regression tests lock this in (`UnitOfWorkBehaviorTests.cs`).

## Performance review

**A real, live-verified performance/correctness bug, found via Playwright under concurrent load, not manual testing**: `ConfirmPaymentCommand`/`ProcessPaymentWebhookCommand` originally awaited the order-confirmation email's full SMTP round trip inline, inside the customer-facing HTTP response. Under a single manual curl this looked survivable (a slow ~6s response); under real concurrent browser load (4 parallel Playwright workers, each placing a real order) it produced a client-observed 499 (browser aborted the request before receiving a response) after ~17.6 seconds — even though the payment had already captured successfully server-side, `Payment.Status == Succeeded`, and the response the customer never saw would have said so. Fixed by making the email send fire-and-forget with `CancellationToken.None`, in both `ConfirmPaymentCommand` and `ProcessPaymentWebhookCommand` (which, investigated as part of the same fix, turned out to never send the confirmation email at all if the webhook — not the customer's own optimistic confirm call — was what actually resolved the payment; a real gap given that command's own doc comment specifically claims "the browser closed right after confirming is recoverable" via the webhook path). `SmtpEmailSender.SendAsync` already catches and logs every internal failure, so the fire-and-forget task can never fault unobserved. See [34_PAYMENTS_NOTIFICATIONS_SEARCH.md](../34_PAYMENTS_NOTIFICATIONS_SEARCH.md)'s own status note.

No N+1 patterns found in the new query handlers — `GetPaymentQuery`/`AdminPaymentSearchQuery` resolve `OrderNumber` via the same batched cross-context repository-lookup pattern `InventoryReservationDto.OrderNumber` established in Sprint 5.4, never one query per row.

## Backend / API / Database review

Every endpoint under `/api/v1/payments/*`/`/api/v1/admin/payments/*` is live, RFC 9457 Problem Details for every new exception type (`PaymentNotFoundException`/`PaymentAttemptNotFoundException` → 404, `PaymentAlreadyExistsException`/`InvalidPaymentStatusException`/`InvalidRefundAmountException`/`PaymentInProgressException` → 409, `InvalidIdempotencyKeyException`/`InvalidPaymentProviderReferenceException`/`InvalidWebhookSignatureException` → 400 — the last one deliberately 400 not 401/403, since a webhook's own signature *is* its authentication), and [37_API_STABILITY_POLICY.md](../37_API_STABILITY_POLICY.md) held with zero Sprint 5.1-5.4 contracts touched (one disclosed, justified exception — see that document's own Sprint 5.5 compliance record). `PaymentPolicy` rate limiting (20/min/IP) applied to the financially-meaningful customer endpoints; the webhook endpoint deliberately unrate-limited, gated by signature verification instead.

One real migration (`AddPayments`) — three new tables (`payments`, `payment_attempts`, `processed_webhook_events`), applied against and verified live via a real `psql \d` inspection against real PostgreSQL, with a unique index on `payments.order_id` (the "one `Payment` per `Order`" invariant enforced at the database level) and a unique index on the converted `IdempotencyKey` column.

## Frontend review

`CheckoutExperience.tsx` now does two real, sequential things instead of one: creates the order (unchanged since Sprint 5.3), then immediately starts a real payment session and hands off to a new step, `PaymentProcessing.tsx` (`/checkout/payment`) — not straight to confirmation. `PaymentProcessing` is idempotent by construction against every real Phase 10 scenario named in this sprint's brief: refresh (re-derives state from `cart-store`'s persisted `lastPaymentId`, re-fetching rather than trusting stale component state), back button (revisiting after a resolved payment safely re-confirms a no-op and re-redirects — verified live via a dedicated Playwright test), and double-click (the backend's own `CreateCheckoutSessionCommand` idempotent-no-op-against-`Processing` guard, unchanged from its original design, still holds). `OrderConfirmation.tsx`'s copy changed from "Order confirmed" to "Payment confirmed" — a deliberate, meaningful distinction now that the page is only reachable after a real charge succeeded — with existing e2e assertions in `cart.spec.ts`/`orders.spec.ts` updated to match, not left pointing at stale copy.

## Accessibility review

New Payments pages reuse this project's existing accessible primitives (`Card`, `Badge`, `Table`, `Select`, `Input`, `Label`, `Button`) — no new hand-rolled controls. `PaymentProcessing.tsx`'s error/decline states use `role="alert"` for the failure message, matching `CheckoutExperience`'s own existing error-announcement pattern. Guard flow (`checking`/`unauthenticated`→redirect/`forbidden`→`AccessDenied`) reuses `useRequireViewOrders`'s established shape via the new `useRequireViewPayments`, not a duplicated mechanism. The public receipt route (`/payments/[id]`) deliberately has no auth-gated layout — same "a guest who just paid can still open their own link" reasoning `GetOrderQuery` already established for guest orders — implemented via a Next.js route group specifically so the sibling history-list route's guard doesn't cascade onto it.

## Lessons learned

Every one of this sprint's real findings, in the order found:

1. `UnitOfWorkBehavior`'s recovery-save path used the request's own cancellable token, silently discarding an already-captured payment on client disconnect (Security review, above). Found via live curl testing after mailhog reachability issues produced a genuinely long-running confirm request.
2. `CapturePaymentCommand` was correct but completely unreachable — no code path ever produced an `Authorized` attempt (Architecture review, above). Found while reasoning through the two-phase flow's real reachability, before it could be rediscovered as a live bug.
3. `StripePaymentGateway.ToOutcome` had no `"requires_capture"` branch, which would have mischaracterized a real approved-but-uncaptured authorization as a failed payment — found and fixed alongside finding 2, same root cause.
4. `PayOrderCommand` had no awareness of an in-flight gateway `Payment`, a real double-charge risk (Security review, above). Found while reasoning through `CancelOrderCommand`'s own interaction with the new Payments context, before it could be discovered live.
5. Every catalog product price and ingredient modifier is a multiple of $0.05, making `FakePaymentGateway`'s magic-cents decline/provider-error convention (`.13`/`.14`) structurally unreachable through any real order — found while planning live decline-path verification, before attempting and failing it live.
6. The order-confirmation email blocked the customer-facing `/confirm` response long enough for a real browser to abort the request under concurrent load, even though the payment had already succeeded (Performance review, above). Found via a real Playwright test failure, not manual testing — the concurrency this test's own multi-worker execution introduced is what actually surfaced it.
7. `ProcessPaymentWebhookCommand` never sent the confirmation email at all, undermining its own doc comment's "browser closed right after confirming is recoverable" claim — found while fixing finding 6, same investigation.
8. `CancelOrderCommand` allows cancelling a `Paid` order with no refund triggered (Architecture review, above) — a real, disclosed, unfixed gap, found while reasoning through Payments' interaction with existing Sprint 5.3 Ordering code.
9. `Payment.TimeoutAttempt` has no real caller — a real, disclosed, unfixed gap, found while writing this sprint's own event-catalog documentation and checking every domain event actually has a live path to being raised.
10. Mailhog's SMTP handshake became unreliable partway through this session, surviving container/stack recreation — a real, disclosed environmental blocker on full e2e verification, found via a live Playwright test timeout and isolated with an independent Python SMTP client to rule out application code.

**Findings 1, 4, 6, and 7 were only found by testing against a genuinely running system under realistic conditions** (a real client disconnect, a real double-submission race, real concurrent browser load) — the same pattern every prior sprint's review has drawn, now extended: a design review or a passing unit-test suite alone would not have surfaced any of these four, since each depends on real timing/concurrency/network behavior no mock reproduces.

## Retrospective

What went well: the `IOrderPaymentCoordinator`/`IInventoryReservationCoordinator` same-transaction pattern generalized cleanly a second time, with zero new architectural negotiation needed — Sprint 5.4's own design decision was validated, not just reused. The `CaptureMode` fix (finding 2) is a genuine example of this project's "no placeholder implementations" rule catching something a passing test suite alone would have missed forever, since `CapturePaymentCommand`'s own unit tests were all correct in isolation — the gap was in what called it, not what it did.

What to carry forward: the "a side effect that must survive regardless of client disconnect needs `CancellationToken.None`, not the request's own token" lesson (findings 1 and 6) is now a real, twice-independently-discovered pattern in this codebase — worth a dedicated note in [41_BACKEND_DEVELOPMENT_STANDARDS.md](../41_BACKEND_DEVELOPMENT_STANDARDS.md) so the next fire-and-forget or recovery-path addition doesn't rediscover it a third time from scratch. The Mailhog/Docker environmental flakiness (finding 10) recurred multiple times across this session even after container-level remediation — worth flagging to whoever owns this dev machine's Docker Desktop setup as a real, recurring friction, not a one-off.

What's explicitly deferred, not forgotten: automatic refund-on-cancel (finding 8); a real background/lazy-sweep caller for `Payment.TimeoutAttempt` (finding 9); live verification of `StripePaymentGateway` against Stripe's real servers (no account/test key exists in this environment — every verification this sprint ran against `FakePaymentGateway`, disclosed throughout rather than glossed over); full e2e re-verification of the registration-dependent specs once the Mailhog/Docker environment is restored (finding 10).

Waiting for the user's review and explicit approval before Sprint 5.6 begins — not started automatically, per this project's established rhythm.
