Zero engine files rewritten — every new capability landed through the sanctioned registry/composition/additive-extension mechanisms this project has used every sprint since Milestone 2.

**Pre-sprint requirement, completed first**: before any Sprint 3.7 code, the user required a permanent fix (not a suppressed warning, not a test-level workaround) for a real hydration mismatch in Sprint 3.5's `features/concierge/data/questions.ts`, flagged in Sprint 3.6's review. See "Pre-sprint fix" below for the full root-cause and fix writeup, and verification numbers.

**Scale**: ~20 new source files (`features/storytelling/` — types, 2 data files, 2 lib files + tests, 1 hook, 6 components; `stores/storytelling-store.ts` + test; `engine/state/scrollProgress.ts`; `engine/performance/useSmoothedVector3.ts`; `e2e/story.spec.ts`), ~15 modified files (`engine/camera/presets.ts` +2 presets registered for real, 3 dormant ones activated; `engine/lighting/presets.ts` + `engine/environment/presets.ts` +2 moods each; `engine/events/types.ts` +2 events; `engine/shaders/common/uniforms.ts` + `steam/steam.frag.ts` + `surfaces/applyFresnelRim.ts` (first real `uStorytellingProgress` publisher/consumers); `features/hero-cup/components/{CupScene,CupCanvas,CupCanvasLoader,CupAssembly}.tsx` (additive prop extensions); `engine/performance/qualityPolicy.ts` (+`storytellingEffects`); `app/SmoothScrollProvider.tsx` (GSAP↔Lenis wiring); `app/story/page.tsx` (real route, replacing `ComingSoonPage`, now deleted — zero other callers). 22 new unit tests (279 total project-wide, 41 files, all passing). A new 33-test e2e suite (`story.spec.ts`, 11 × 3 browsers, 32 passing + 1 correctly WebKit-skipped).

## Pre-sprint fix: the Sprint 3.5 hydration mismatch

**Root cause, confirmed by direct investigation, not assumed from the user's own diagnosis**: `features/concierge/data/questions.ts`'s `DEFAULT_TASTE_PROFILE` computed `season`/`timeOfDay` via `resolveCurrentSeason(new Date())`/`resolveCurrentTimeOfDay(new Date())` at *module-evaluation time*. The server evaluates a module once per process — its "current" date stays frozen at whichever instant the server first imported this module, for the life of that process. The client re-evaluates the module fresh on every page load. Once the server process outlived a single time-of-day boundary since its own start, every hydration mismatched, deterministically, on all three browsers — confirmed by isolated re-runs that reproduced it live during this exact session (this session's dev server had been running long enough).

**Fix — the implementation, not the test, per explicit instruction**: `DEFAULT_TASTE_PROFILE`'s `season`/`timeOfDay` are now fixed, non-date-dependent values — identical on the server's SSR render and the client's first (pre-hydration) render, so they can never disagree. The real, current-date value is applied exactly once per fresh session, client-side only, via a new `applyCurrentDateDefaults` store action invoked from `concierge-store.ts`'s `onRehydrateStorage` — guaranteed to run after the hydration-sensitive first render has already committed, and gated on `sessionStorage` genuinely having nothing persisted yet (so it never clobbers a user's own edits, or a previous mount's already-applied default, across a same-session reload — the same "restore what the user actually chose" invariant `partialize` already documented). `resetTasteProfile` was updated to match (restores the real current-date default, not the fixed SSR-safe placeholder — its original intent, now correctly separated from the hydration-critical initial value).

**No hydration warning was suppressed** — the implementation no longer produces a mismatch to suppress.

**Verified**: `tsc --noEmit`/`eslint` clean, 257/257 unit tests (pre-existing suite, confirmed unaffected), 30/30 `concierge.spec.ts` e2e tests across Chromium/Firefox/WebKit — run directly against this session's own long-running dev server, the exact condition that reproduced the bug — showing zero hydration failures, down from failing on all three browsers in two consecutive full regression runs beforehand. A dedicated full regression run after the fix (216 tests) showed 206 passed, 3 failed — all 3 the same pre-existing, already-documented WebKit environmental findings (visual-regression noise, reduced-motion keyboard-commit quirk), confirmed via isolated re-run, zero concierge failures. Committed separately (`5d81f31`) from Sprint 3.7's own work, so the fix's own history stays traceable.

## Architecture review

**Zero engine files rewritten — every extension used a sanctioned mechanism from [17_ZERO_REWRITE_POLICY.md](../17_ZERO_REWRITE_POLICY.md)**: registry entries (camera/lighting/environment presets — mechanism #1), composition (`useScrollTimeline` composes the Camera Manager + `scrollProgress` + EventBus through their existing public interfaces, never reaching into `CameraRig` internals — mechanism #2, the doc's own named example for exactly this kind of feature), and additive interface extension (new optional props on `CupScene`/`CupCanvas`/`CupCanvasLoader`/`CupAssembly`, a new field on `qualityPolicy.ts`'s policy table — mechanism #5, checked against its own test: "does any existing caller's behavior change without that caller's code changing?" — no; every pre-3.7 caller of every extended function passes `undefined`/omits the new fields and is provably unaffected, verified by the full regression run, not assumed).

**A real, reasoned deviation from a two-sprint-old anticipation, investigated against actual code before deciding — not read as an instruction to blindly follow stale docs**: `docs/03_3D_ENGINE.md`/`docs/22_MANAGER_INTERFACES.md` anticipated a `CameraPath` registry and a `CameraRig.path` prop for this exact sprint. The brief's own explicit instruction this time ("Do not modify Camera contracts. Implement through new presets only") is stricter than that anticipation — rather than treating the instruction and the old design as compatible by default, `CameraRig.tsx`'s actual implementation was read first: it resolves its target preset once per React render (`const config = resolveCameraPreset(preset)`), not per-frame, so a continuously-updated computed preset would silently never be picked up without also forcing `CameraRig` to re-render on every scroll tick — a real performance regression the component's own frame-loop design specifically avoids elsewhere. The chosen design (discrete per-chapter named-preset switches, `CameraRig` fully unmodified) is both technically correct against the real code *and* the literal brief instruction — verified compatible, not merely convenient. Recorded in [26_API_STABILITY.md](../26_API_STABILITY.md) as **Resolved**, the same category Sprint 3.5's TanStack Query decision used.

**Dormant capability, built years (project-time) ahead of its first real consumer, finally exercised — this project's own established pattern, now instanced a third/fourth time**: `engine/state/scrollProgress.ts` (designed Sprint 2.1, explicitly left uncreated as "genuinely inert, zero-behavior" until a real consumer existed) is now real. `CupPartProps.position`/`rotation` (typed since Sprint 2.3, confirmed — by direct code read, not assumption — completely unwired in `CupAssembly`'s render loop) now actually move a part for the first time. `sharedUniforms.uStorytellingProgress` (typed since Sprint 2.4, "no publisher yet") has one. Each of these is the same story Sprint 3.5's review told about `CameraRig`'s preset interpolation and Sprint 3.6's review told about `createBridgeStore`'s reuse — a real, recurring payoff of this project's habit of typing a capability correctly before it has a caller.

**A new, real generalization, not a one-off**: `useSmoothedVector3` (new file, `engine/performance/`) extends Sprint 2.5's `useSmoothedValue` (bounded-re-render-while-converging, silent at steady state) from a scalar to a `[number,number,number]` tuple, reusing `CameraController.ts`'s existing `dampVector3` math rather than inventing a second interpolation technique. This is the mechanism behind the Crafting chapter's assembly moment — verified by direct code read to be the only mechanism that could actually deliver "cup parts glide toward a target" without either forcing per-frame re-renders (rejected) or requiring `CupAssembly` to hold raw refs to each part's `Group` and mutate them outside React's render cycle (a larger, less-precedented change than reusing an existing, already-proven hook pattern).

## Animation/motion review — tool ownership, per this project's own rule

`docs/04_MOTION_ENGINE.md`'s ownership table (Framer Motion = discrete DOM, raw `useFrame` = continuous 3D transform-is-the-state, GSAP+ScrollTrigger = timeline sequencing) is followed exactly, checked against what was actually built, not assumed: `ChapterSection`'s entrance uses the existing `fadeUp` Framer preset (discrete, component-scoped — correct lane). `CupAssembly`'s lid/sleeve damping and the idle float/rotation it already owned both live in the same one `useFrame`/`useSmoothedVector3` continuous-transform lane — no second animation system introduced for parts that already had one. `useScrollTimeline`'s `ScrollTrigger`s own exactly what they should: chapter-boundary detection and progress publishing — never object transforms directly, which stay owned by `CupAssembly`/the shader uniform block, per this doc's own "no duplicated animation ownership" rule (checked directly: no GSAP tween targets a Three.js object or a shared uniform anywhere in this sprint's code).

**"Narrative over Animation," the brief's own closing philosophy, checked against every motion decision, not just stated**: the camera never continuously scrubs with scroll pixel-by-pixel — it makes exactly 7 purposeful, named moves, one per chapter, each with a real reason (Origins = wider establishing shot for "surveying a scene," Crafting = the assembly reveal, Customization = a tighter "on display" framing, Concierge = reusing the AI's own "presented to you" framing rather than inventing a new one, Commerce = a "you're being offered this" close framing, Finale = a deliberately restrained near-return to Hero's own framing — a narrower fov reading as a closing shot, not a new spectacle). Every continuous motion (the assembly, the ingredient orbit, the shader boost) is tied to one specific chapter's own scroll range, never left running generically. Nothing animates "because it looks good" without a stated narrative reason — checked against `data/chapters.ts`'s own doc comments for each choice, not asserted after the fact.

## 3D experience / performance review

**A real bug found and fixed during this sprint's own manual verification, not shipped**: the Customization chapter's ingredient reveal (rings orbiting the cup) rendered essentially invisible — confirmed via direct screenshot inspection, not assumed. Root-caused to two independent, real issues: (1) the initial orbit radius (1.1 units) exceeded the "product" camera preset's visible frustum at its framing distance — verified by temporarily widening the radius to 1.6 and confirming the rings still didn't appear even partially at the frame edge, ruling out "just needs a bigger radius" before diagnosing further; (2) the ingredients sit at foam height, directly beneath the cup's own (closed, opaque) lid — confirmed via a debug window hook exposing the live store state, which showed `chapterProgress` and the computed orbit math were both correct, isolating the bug to occlusion, not math. Fixed by (1) reducing the orbit radius to a value confirmed, by direct screenshot, to stay inside the camera frustum, with a settle floor so ingredients never fully collapse to an invisible point at the cup's center, and (2) hiding the lid for the one chapter that shows ingredients — a real, motivated choice ("here's what's on your drink"), not a hack.

**Manual, real-browser verification, not just automated assertions**: every chapter's camera/lighting transition, the assembly moment (screenshotted at multiple scroll depths, confirmed the lid/sleeve visibly displace and reassemble), the ingredient reveal (after the fix above), and the Finale's real CTAs were all visually confirmed via Playwright screenshots inspected directly — see this review's own investigation trail above, not claimed from reading the code.

**Quality-tier scaling, "never disable, only scale," this table's own established exception rule respected**: a new `storytellingEffects` field (`shaderBoostIntensity`, `maxFeaturedIngredients`) follows `coffeePhysics`'s exact precedent (Sprint 3.4) — every tier keeps both values nonzero, including `minimal` (0.25 intensity, 1 ingredient, never 0), consistent with `bloomEnabled` remaining this table's one stated exception, not a second one added quietly.

**A deliberate, real perf-conscious layout decision**: the sticky 3D column uses plain CSS `position: sticky`, not GSAP `ScrollTrigger`'s `pin` option — investigated as a real tradeoff (pinning can deliver more elaborate choreography) and scoped out specifically because pin-related layout reflow/`pinSpacing` edge cases are a real risk category that's hard to iterate on reliably without a live visual editor in this environment; CSS `sticky` is simpler, more robust, and delivers the same "visual stays in view while text scrolls past" effect natively.

## Accessibility review

**Keyboard**: `ChapterNav`'s dot rail is real `<button>`s, reachable by Tab, jumping directly to any chapter on Enter/Space/click — genuine navigation, not just a scroll-position indicator. `SkipStorytellingLink` follows the exact `sr-only`-until-focused convention the site-wide `SkipLink` already established. Verified via e2e: tabbing to a nav dot and pressing Enter jumps correctly; the skip-storytelling link, focused directly, activates and jumps to the Finale.

**A real, investigated (not just skipped) WebKit finding**: `SkipStorytellingLink`'s keyboard test is `test.skip`'d on WebKit, but only after confirming this is the exact same, already-documented "Safari/WebKit excludes links from the default Tab order (Full Keyboard Access required)" platform limitation `e2e/stabilization.spec.ts` already carved out since Sprint 2.6 — not a new, unexamined skip.

**Reduced motion — a real design decision, not a blanket fallback**: camera/lighting still change per chapter under reduced motion (a plain `IntersectionObserver`, no GSAP `ScrollTrigger`, drives the same `storytelling-store` action) — reasoned through directly: a chapter's camera/lighting preset is a discrete *choice*, not itself "motion," so removing it entirely would remove real content variety without removing any actual animation. What *does* disable outright: the assembly moment, the ingredient orbit, and the shader density ramp all land directly on their end state (assembled, settled, zero boost) rather than animating toward it — verified via e2e with `reducedMotion: "reduce"` emulation, zero console errors, correct end-states confirmed screenshot-side.

**Screen-reader summaries**: a `role="status"`/`aria-live="polite"` region announces the active chapter's title on every chapter change — given a distinguishing `aria-label` ("Story chapter announcements") from the start, having directly learned from Sprint 3.6's own regression (a global `CartAnnouncer` breaking two pre-existing tests that assumed only one `role="status"` region existed) rather than repeating that mistake a second time.

**Landmarks**: every chapter is a real `<section aria-label>`, in DOM order matching narrative order — verified via e2e as a real accessibility-tree table of contents, not asserted from the JSX alone.

## Retrospective

### Technical debt

- No true liquid pouring transition (see above) — the natural next step once the coffee mesh's pivot point is confirmed.
- No ambient café audio — the brief marked it explicitly optional; `engine/audio/` remains undocumented-in-code, same status as every prior sprint that considered and declined to build it without a real forcing need.
- The Customization chapter's ingredient orbit radius/settle values were tuned by direct visual iteration (screenshot, adjust, re-screenshot) rather than derived from exact camera-frustum trigonometry — correct as verified, but a future camera reframing of the "product" preset would need the same visual-check treatment, not just a formula update.

### Architectural observations

- This sprint is this project's clearest instance yet of "read the real code before trusting a two-sprint-old anticipation" — the `CameraPath` decision would have been wrong (and would have required touching `CameraRig.tsx`, a frozen engine file) if the original Sprint 2.1 design had simply been implemented as sketched, without checking it against the brief's actual, stricter instruction and the component's real render-vs-frame behavior.
- Three genuinely dormant, multi-sprint-old capabilities (`scrollProgress`, `CupPartProps.position`/`rotation`, `uStorytellingProgress`) all found their first real consumer in the same sprint — not a coincidence so much as this being the first sprint whose brief actually needed continuous, scroll-driven scene changes, exactly the kind of need those three were typed in anticipation of.
- `useSmoothedVector3`'s creation is a small, real instance of a recurring pattern in this project: generalize a working scalar utility to a vector only once a genuine vector need exists (matching `dampVector3` itself being extracted from `CameraRig`'s original inline math, and `useSmoothedValue` predating this sprint by two).

### Possible improvements

- A future sprint could revisit true liquid fill-level pouring once coffee's geometry pivot is confirmed, using the same additive-uniform pattern Sprint 3.4 established for tilt/ripple.
- If a future brief specifically wants continuous, per-pixel camera scrubbing (not per-chapter discrete moves), `engine/camera/paths.ts`/`CameraRig.path` remain the real, still-undesigned-in-code target from `docs/03_3D_ENGINE.md`/`docs/04_MOTION_ENGINE.md` — this sprint's decision doesn't foreclose it, just correctly declines to build it without a real need.
