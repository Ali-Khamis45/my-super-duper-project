# Sprint 5.1 — Authentication & Identity Platform: Review

The first real backend this project has ever shipped — a Clean Architecture ASP.NET Core 10 solution (`backend/`) implementing every contract frozen in Milestone 5 Phase 0: the `User`/`RefreshToken`/`EmailVerificationToken`/`PasswordResetToken`/`RoleDefinition`/`Permission` domain model ([30_COMMERCE_DDD_MODEL.md](../30_COMMERCE_DDD_MODEL.md)), all 10 auth endpoints ([31_COMMERCE_ENGINEERING_CONTRACTS.md](../31_COMMERCE_ENGINEERING_CONTRACTS.md)), the outbox-pattern schema ([32_COMMERCE_EVENT_CATALOG.md](../32_COMMERCE_EVENT_CATALOG.md)), the JWT/rotating-refresh-token/RBAC design ([33_AUTH_ARCHITECTURE.md](../33_AUTH_ARCHITECTURE.md)), and the security controls ([36_SECURITY_MODEL.md](../36_SECURITY_MODEL.md)) — plus real frontend integration (`lib/auth-client.ts`, `stores/auth-store.ts`, five new routes, an additive navbar `AccountMenu`) under an unmodified Zero Rewrite Policy. Verified against a real PostgreSQL database, real SMTP delivery (Mailhog), and a real browser (Playwright) — not mocks. Six real backend bugs and one real frontend regression were found and fixed via this verification, detailed below.

**Scale**: `backend/` — 7 source projects (`Coffeshop.{SharedKernel,Domain,Application,Persistence,Identity,Infrastructure,Api}`) + 3 test projects, ~90 new source files, one EF Core migration, a `docker-compose.yml` dev stack (Postgres/Redis/Mailhog/Seq), a new `docs/41_BACKEND_DEVELOPMENT_STANDARDS.md`. 42 backend tests (30 Domain, 6 Application, 6 Integration), all passing. Frontend: 8 new files (`lib/auth-client.ts`, `stores/auth-store.ts`, 6 `features/auth/components/*`), 5 new routes, 2 modified files (`app/providers.tsx`, `Navbar.tsx`), a new `e2e/auth.spec.ts` (5 tests), one line fixed in `e2e/stabilization.spec.ts`. `tsc`/`eslint`/`next build` clean; 280 pre-existing Vitest tests still passing (zero regression).

## Architecture review

**Clean Architecture's layer boundary is a compiler error, not a convention, and it held immediately**: `Coffeshop.Domain` has zero package references beyond `Coffeshop.SharedKernel`; `Coffeshop.Application` has zero reference to EF Core, ASP.NET Core, or any concrete infrastructure. This was checked directly (the solution simply doesn't compile if violated), not asserted from a diagram — the same discipline the frontend's `engine/` layer boundary has held since Milestone 1.

**The "one aggregate per transaction" rule held with zero exceptions this sprint** — `User` is the only aggregate root; every command loads and saves exactly one `User`. The rule's first real test (a cross-aggregate exception, `Coupon`/`Order`) is Sprint 5.3 work, not this one.

**Two real, reasoned deviations from the frozen design**, both because implementation revealed something the design phase couldn't have known without building it:

1. **No separate `Session` entity.** [33_AUTH_ARCHITECTURE.md](../33_AUTH_ARCHITECTURE.md) already specified "each `RefreshToken` *is* a session" — a later brief also asked for a distinct Session entity in the same phase. Resolved in favor of the already-frozen design: `RefreshToken` carries `DeviceName`/`UserAgent`/`CreatedAtUtc`/`LastUsedAtUtc` directly, and a second, competing entity was never built. Doc updated to record this explicitly rather than leaving two docs in silent disagreement.
2. **Reuse-detection scoped to rotation, not any revocation** — see Security review below; this is the sprint's most consequential finding.

**Repository contracts didn't extend a shared generic base this sprint** — `IUserRepository`/`IRoleRepository` are standalone interfaces, not `: IRepository<TAggregate, TId>`. [31_COMMERCE_ENGINEERING_CONTRACTS.md](../31_COMMERCE_ENGINEERING_CONTRACTS.md)'s generic base remains the intended shape; a two-aggregate Identity context didn't produce enough shared surface to justify the extra indirection yet. Revisited honestly once Sprint 5.2 adds `Product`/`Ingredient`/`Category` and there's real evidence either way.

**The outbox pattern's publish side is real; the dispatcher is correctly deferred.** `DomainEventsToOutboxInterceptor` drains every pending domain event into the `outbox_messages` table in the same `SaveChangesAsync` call that changed the aggregate — verified directly via `dotnet ef migrations add` producing the real schema and a live `INSERT INTO outbox_messages` observed during manual testing. The Hangfire polling dispatcher was not built, because Sprint 5.1 has zero real event consumers (a fresh Identity context has no other bounded context to notify yet) — building a dispatcher with nothing to dispatch to would have been exactly the "half-finished code" this project's own standards forbid.

## Security review

**The most important finding this sprint, found by hand, not by any test**: manually testing `/revoke-session` followed immediately by `/refresh` with that same session's now-revoked cookie triggered reuse-detection's full revoke-all response — killing every *other* session too, not just the one the user deliberately ended. [33_AUTH_ARCHITECTURE.md](../33_AUTH_ARCHITECTURE.md)'s design said "a revoked token presented again" triggers revoke-all, without distinguishing *why* it was revoked. The fix narrows this correctly: only a token revoked *by rotation* (`ReplacedByTokenId` set — the actual theft signal, since a legitimate holder's token is only ever revoked that way) triggers the security response; a token revoked by logout, explicit session revocation, or password reset presented again is just a stale cookie, an ordinary 401. Locked in by two tests: `RotateRefreshToken_TokenAlreadyRotatedAway_ThrowsReuseDetectedAndRevokesEverySession` and `RotateRefreshToken_TokenRevokedByLogoutNotRotation_ThrowsInvalidTokenWithoutRevokingOtherSessions`, plus a live-cascade integration test exercising the real HTTP flow (register → verify → login on two "devices" → rotate device A → replay device A's stale cookie → confirm reuse-detection fires *and* device B is now also dead).

**A second, more structural finding**: `UnitOfWorkBehavior`'s original "save only after the handler returns successfully" logic meant reuse-detection's revoke-all mutation — the actual security response — was silently discarded, since the handler throws *after* mutating. The fix (`try`/`catch` around `SaveChangesAsync`, saving on both the happy path and the throw path, logging but not masking a secondary save failure) makes "mutate, then throw a business exception" — a legitimate, common domain pattern this project's own exception-handling rules already assume — actually work. Without this fix, the reuse-detection fix above would have been correct in memory and silently ineffective in the database.

**Passwords**: `PasswordHasher<User>` (ASP.NET Core Identity's own utility class, PBKDF2), never a custom hash, verified by a real registered account's password surviving a server restart and rejecting the old password after a reset.

**Tokens at rest**: every refresh/verification/reset token is stored as its SHA-256 hash (`token_hash` columns, verified directly via `psql`) — the raw value exists only in the HttpOnly cookie and the moment it's minted server-side, never logged (confirmed `EnableSensitiveDataLogging()` was a temporary debugging aid, removed before this sprint closed, not left enabled).

**Account enumeration**: `/login` and `/forgot-password` both return generically regardless of whether the account exists — verified directly (`forgot-password` for a real vs. fake email returns identical 202s; `login` for a wrong password vs. no such account returns identical 401s).

**CORS**: credentialed (cookie-bearing) requests require an explicit named origin, never `*` — verified via a real preflight (`OPTIONS` with `Origin: http://localhost:3000`) returning `Access-Control-Allow-Credentials: true` scoped to exactly that origin.

**Rate limiting**: the `auth` policy's 10-requests/minute ceiling was hit and correctly returned `429` during manual testing (11 rapid `/forgot-password` calls → 2× 202, 9× 429).

## Performance review

No load testing this sprint (correctly out of scope — Sprint 5.6's job, once there's a real deployed environment and more than one endpoint family to load-test meaningfully). What was verified: every read query uses `AsNoTracking()`-eligible patterns where the result isn't mutated in the same request; the `refresh_tokens`/`email_verification_tokens`/`password_reset_tokens` hash-lookup columns are uniquely indexed (confirmed in the generated migration, not assumed); `RoleIds`/`PermissionCodes` are native PostgreSQL arrays (`uuid[]`/`text[]`), not a JSON-serialized blob requiring deserialization on every read.

## Accessibility review

Every new form (`LoginForm`, `RegisterForm`, `ForgotPasswordForm`, `ResetPasswordForm`) uses explicit `<label htmlFor>`/`<input id>` pairing, matching `CheckoutExperience.tsx`'s already-established convention — caught by this project's own `jsx-a11y/label-has-associated-control` lint rule for two of the four forms (the implicit-nesting pattern doesn't reliably trace through the `Input` wrapper component), fixed project-wide for consistency rather than only where the linter happened to catch it. Validation errors (`role="alert"`) and success states use real semantic elements, not styled `<div>`s. `AccountMenu` renders a stable-sized placeholder during the `idle`/`restoring` auth-status window specifically to avoid a layout shift/flash from "nothing" to "Log in" to a user avatar on every page load.

## Regression review

**280 pre-existing Vitest unit tests**: unaffected, zero changes needed.

**A real regression found and fixed via the existing e2e suite, not just the new one**: `stabilization.spec.ts`'s strict zero-console-errors hero-smoke test started failing after `AuthSessionRestorer` was wired into `Providers` — an anonymous visitor's silent session-restore attempt (`POST /api/v1/auth/refresh` with no valid cookie) correctly returns 401, and a browser logs *any* non-2xx `fetch` response as a "Failed to load resource" console error regardless of the app's own try/catch around it — this is unavoidable browser-level behavior, not something app code can suppress. Fixed by filtering this one, specifically-matched, expected message out of that test's assertion — the same "filter a known error by name rather than loosen the check" precedent Sprint 3.6's review already established for the frozen Engine v1.0's HDRI-fetch-abort finding.

**A real, useful finding while writing the new e2e suite itself**: Base UI's `Button` primitive exposes `role="button"` in the accessibility tree even when rendered as an anchor (`render={<Link href="..." />}`) — querying by `role: "link"` for the navbar's "Log in" control finds nothing, despite it genuinely being an `<a href="/login">`. Not a bug (a deliberate, defensible choice by Base UI — the element *behaves* like a button-triggered navigation, not a plain content link), but a real trap for any future test in this codebase using `render={<Link />}` — worth knowing project-wide, noted in the test file itself.

## API review

Every endpoint in [31_COMMERCE_ENGINEERING_CONTRACTS.md](../31_COMMERCE_ENGINEERING_CONTRACTS.md)'s catalog is live at exactly its frozen path/verb, versioned under `/api/v1/`. Error responses are RFC 9457 Problem Details exclusively, verified directly (`{"type":"https://coffeshop.dev/errors/invalid-credentials", ...}`), including field-level validation errors matching the frozen `errors` dictionary shape. `UserDto`'s real shape (`id, email, fullName, isEmailVerified, roles: string[], permissions: string[]`) matches what [31_COMMERCE_ENGINEERING_CONTRACTS.md](../31_COMMERCE_ENGINEERING_CONTRACTS.md) anticipated. No endpoint's contract changed after being frozen — [37_API_STABILITY_POLICY.md](../37_API_STABILITY_POLICY.md) had nothing to enforce against yet, since this is the first sprint to ship any of it, but the discipline (additive-only DTOs, versioned routes) was followed from the first commit, not retrofitted.

## Lessons learned

**Every one of this sprint's six backend bugs was found by actually running the system, not by reading code or by static analysis** — `tsc`/`dotnet build`/`eslint` were clean throughout, and every bug still shipped in the first pass:

1. EF Core cannot translate `u.Email.Value == x` through a value-converted property — comparisons must be against the whole VO (`u.Email == Email.Create(x)`), letting EF apply the converter to both sides.
2. A client-generated Guid key on an owned entity needs `.ValueGeneratedNever()` explicitly, or EF Core's default convention misjudges a brand-new entity as already-existing and emits an `UPDATE` instead of an `INSERT`.
3. Reuse-detection needed to distinguish *why* a token was revoked (Security review, above).
4. `UnitOfWorkBehavior` needed to save on the throw path, not just the happy path (Security review, above).
5. `AddValidatorsFromAssembly` only finds `public` validator classes (`GetExportedTypes()`) — every validator in this codebase must be public, never `internal`, despite handlers correctly staying `internal`. An `internal` validator compiles clean and is silently never registered; an empty password registered successfully with zero errors anywhere until caught by manually calling the endpoint.
6. A JWT signing key read eagerly (`configuration.GetSection(...).Get<T>()`, evaluated once at service-registration time) can capture a stale configuration snapshot if any config source layers in afterward — reading it lazily via `IOptions<T>` (resolved at first use, after every source has merged) is the correct, general fix, not just a test-environment workaround. This one was caught specifically *by* the integration test suite, not by manual curl testing, which is the clearest evidence this sprint has for why both kinds of verification earned their place — manual testing found 5 bugs the automated suite didn't have yet; writing the automated suite immediately found a 6th that manual testing, by coincidence of a consistently-available dev signing key, never would have surfaced.

**The backend/frontend integration boundary worked exactly as ADR-0015 predicted**: zero existing frontend file needed a shape change — `Navbar.tsx` gained one new child component, `providers.tsx` gained one new mounted component, no existing store, route, or component touched a line of its own logic.

## Retrospective

What went well: the DDD/Clean Architecture layering caught real design questions early (the repository-generic-base deferral, the outbox dispatcher scoping) rather than after code existed to be broken by getting them wrong. Live verification against a real database, real SMTP, and a real browser — not mocks at any layer — is what actually found six of this sprint's real bugs; a mock-heavy test strategy would have hidden every one of them (the EF translation bug, the owned-entity insert bug, and the JWT lazy-config bug are all specifically about real-database/real-DI behavior a mock can't reproduce).

What to carry forward: the "manual verification first, then automated tests to lock in the fix" order used throughout this sprint found bugs faster than writing exhaustive tests up front would have — but the JWT lazy-config bug (found only by the integration suite, invisible to manual curl testing because a `dotnet user-secrets`-provided signing key happened to be consistently available in every manual test run) is the concrete argument for never treating manual verification as sufficient on its own. Both are load-bearing; neither replaces the other.

What's explicitly deferred, not forgotten: the outbox dispatcher (Sprint 5.3+, once real consumers exist), `IRepository<TAggregate, TId>`'s literal generic inheritance (revisit at Sprint 5.2), GDPR/CCPA data export (accepted gap per [36_SECURITY_MODEL.md](../36_SECURITY_MODEL.md), no named requirement yet), and `LoginFailed` as its own auditable event (currently only logged, not a distinct domain event — a small, real gap worth a one-line fix in a future sprint, not urgent enough to hold this one up).

Waiting for the user's review and explicit approval before Sprint 5.2 (Product Platform) begins — not started automatically, per this project's established rhythm.
